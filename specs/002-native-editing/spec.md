# Спецификация функции: Нативное редактирование рецепта (Phase 3)

**Feature Branch**: `002-native-editing`

**Created**: 2026-06-01

**Status**: Draft

**Input**: Phase 3 Recipe Scaler Native — нативное редактирование полей рецепта через Y.Doc с отправкой изменений на сервер (iOS → web), офлайн-очередь и debounce как у веб-клиента. Без редактора описания (Phase 4).

**Зависимости**: Phase 2 (`001-yrs-native-read`) завершена — чтение коллекции и рецептов из Y.Doc, приём обновлений web → iOS подтверждено.

## Политика версий рецептов

| Версия | Чтение (Phase 2) | Редактирование (Phase 3) |
|--------|------------------|---------------------------|
| **v3** | Да | Да — полный scope Phase 3 |
| **v1, v2** | Да (как сейчас) | **Нет** — только просмотр |

- Рецепты **v1/v2** на iOS **не редактируются**. Миграция на v3 выполняется **в веб-клиенте**, не в нативном приложении.
- При открытии рецепта v1/v2 приложение показывает **информационный баннер** (i18n): устаревший формат, только чтение; предложение обновить рецепт в вебе.
- Все элементы ввода и действия «Сохранить» для таких рецептов **отключены** (read-only mode).
- Запись в Y.Doc (мутации, `sync_request`, офлайн-очередь) разрешена **только** для `version == v3`.

### Обязательные элементы интерфейса (уровень спеки)

- **FR-UI-001**: Для рецепта **v3** — явный режим редактирования полей рецепта (название, порции, цвет) и ингредиентов; для **v1/v2** — только просмотр.
- **FR-UI-002**: Баннер «устаревший формат, только чтение» для v1/v2 вверху экрана деталей; не блокирует прокрутку контента.
- **FR-UI-003**: Индикатор состояния записи/синхронизации (локально / отправка / синхронизировано / ошибка) в зоне деталей рецепта v3.
- **FR-UI-004**: Действия добавления/удаления/изменения ингредиента доступны только для v3.
- **FR-UI-005**: Все пользовательские строки — через i18n (ru/en), включая текст баннера и статусы sync.

*Конкретные контролы (TextField inline, swipe-delete, отдельный экран редактирования ингредиента и т.д.) — в `plan.md` после `/speckit-plan`.*

## Пользовательские сценарии и тестирование *(mandatory)*

### Пользовательская история 0 — Просмотр рецепта устаревшего формата (Приоритет: P1)

Пользователь открывает рецепт v1 или v2 и видит данные в режиме только чтения с понятным объяснением, почему нельзя редактировать на iOS.

**Обоснование приоритета**: Снижает риск порчи legacy-документов; согласовано с миграцией через веб.

**Независимое тестирование**: Открыть v1-рецепт — баннер виден, поля нельзя изменить, масштабирование слайдером по-прежнему работает как UI-local.

**Сценарии приёмки**:

1. **Если** `version` рецепта v1 или v2, **Когда** пользователь открывает детали, **Тогда** отображается баннер «только чтение» и нет активных кнопок сохранения/добавления ингредиента
2. **Если** рецепт v1/v2, **Когда** пользователь пытается изменить название, **Тогда** изменение не применяется и не отправляется на сервер
3. **Если** тот же рецепт мигрирован в вебе до v3, **Когда** iOS получает обновление документа, **Тогда** баннер исчезает и становится доступно редактирование без переустановки приложения

---

### Пользовательская история 1 — Редактирование основных полей рецепта v3 (Приоритет: P1)

Пользователь открывает рецепт на iOS и меняет название, количество порций или цвет. Изменения сохраняются в документе рецепта и через несколько секунд видны в веб-клиенте на том же аккаунте.

**Обоснование приоритета**: Минимальный сквозной путь «iOS пишет → сервер → web читает». Без этого нельзя проверить обратную синхронизацию и ценность Phase 3.

**Независимое тестирование**: Открыть **v3**-рецепт на iPhone, изменить название или порции, обновить веб — поля совпадают.

**Сценарии приёмки**:

1. **Если** рецепт **v3** загружен и приложение онлайн, **Когда** пользователь меняет название рецепта и сохраняет, **Тогда** веб-клиент показывает новое название в течение 5 секунд
2. **Если** рецепт с 4 порциями, **Когда** пользователь меняет порции на 6, **Тогда** значение `servings` в Y.Doc обновляется и отображается на вебе; локальный слайдер масштабирования ингредиентов по-прежнему считается от UI, не записывая отдельный «scaleFactor» в документ
3. **Если** пользователь меняет цвет рецепта, **Когда** изменение применено, **Тогда** цвет в списке и деталях совпадает на iOS и вебе после синхронизации

---

### Пользовательская история 2 — Редактирование ингредиентов v3 (Приоритет: P2)

Пользователь добавляет, изменяет, удаляет и упорядочивает ингредиенты в рецепте на iOS. Состав рецепта синхронизируется с веб-клиентом с сохранением `originalAmount` для последующего масштабирования.

**Обоснование приоритета**: Ингредиенты — ядро продукта; без CRUD по ингредиентам редактирование неполноценно.

**Независимое тестирование**: Изменить один ингредиент и добавить новый на iOS — веб показывает тот же список с теми же полями (имя, количество, порядок).

**Сценарии приёмки**:

1. **Если** рецепт **v3** открыт, **Когда** пользователь редактирует количество существующего ингредиента, **Тогда** обновлённые `amount` и `originalAmount` видны на вебе
2. **Если** рецепт **v3** открыт, **Когда** пользователь добавляет новый ингредиент, **Тогда** ингредиент появляется в веб-клиенте с уникальным id и корректным `order` в `Y.Array` of `Y.Map`
3. **Если** рецепт v3 содержит несколько ингредиентов, **Когда** пользователь удаляет один ингредиент, **Тогда** он исчезает из списка на iOS и вебе после синхронизации

---

### Пользовательская история 3 — Редактирование питательной ценности v3 (Приоритет: P3)

Пользователь задаёт или обновляет калории, белки, жиры и углеводы рецепта на iOS; значения синхронизируются с веб-клиентом.

**Обоснование приоритета**: Питание — отдельный блок данных в схеме; нужен паритет с вебом, но не блокирует MVP редактирования полей и ингредиентов.

**Независимое тестирование**: Изменить калории на iOS — веб показывает те же числа в блоке nutrition.

**Сценарии приёмки**:

1. **Если** у рецепта нет nutrition, **Когда** пользователь вводит калории и макронутриенты, **Тогда** блок nutrition появляется на вебе после синхронизации
2. **Если** nutrition уже задана, **Когда** пользователь меняет белки, **Тогда** обновлённое значение видно на iOS и вебе

---

### Пользовательская история 4 — Редактирование в офлайне с последующей отправкой (Приоритет: P4)

Пользователь вносит изменения без сети; приложение сохраняет их локально и автоматически отправляет на сервер при восстановлении связи, без потери правок и без ручного «синхронизировать».

**Обоснование приоритета**: Constitution требует offline-first; Phase 2 дал только чтение офлайн, Phase 3 должен завершить цикл для мутаций.

**Независимое тестирование**: Авиарежим → изменить название **v3**-рецепта → выйти в сеть → веб показывает новое название без повторного ввода.

**Сценарии приёмки**:

1. **Если** приложение офлайн, **Когда** пользователь сохраняет изменение рецепта, **Тогда** UI сразу отражает правку из локального Y.Doc, а в очереди офлайн-операций появляется отложенная отправка
2. **Если** в очереди есть неотправленные обновления, **Когда** сеть восстанавливается, **Тогда** очередь сливается на сервер в течение 10 секунд и веб получает итоговое состояние
3. **Если** во время офлайна пришли бы правки с другого устройства, **Когда** приложение снова онлайн, **Тогда** локальные и удалённые изменения сходятся через CRDT без диалога «выберите версию»

---

### Пользовательская история 5 — Согласованная отправка и обратная связь (Приоритет: P5)

Приложение не «засыпает» сервер частыми мелкими пакетами при быстром вводе и сообщает пользователю о сбоях синхронизации (ошибка владения, удалённый рецепт), не оставляя UI в ложном состоянии «всё сохранено».

**Обоснование приоритета**: Паритет с веб-клиентом (debounce ~1 с) и предсказуемая обработка `sync_error` уже заложены в Phase 2 для чтения — для записи нужны те же правила.

**Независимое тестирование**: Быстро изменить несколько полей подряд — на веб уходит сгруппированное обновление; симулировать `sync_error` — показать понятное сообщение.

**Сценарии приёмки**:

1. **Если** пользователь быстро меняет несколько полей, **Когда** пауза ввода ~1 секунда, **Тогда** на сервер уходит не более одного объединённого обновления за такой цикл (аналог debounce веб-клиента)
2. **Если** сервер отвечает ошибкой владения, **Когда** отправка отклонена, **Тогда** пользователь видит локализованное сообщение об ошибке, а локальные данные не считаются успешно синхронизированными с сервером
3. **Если** рецепт помечен удалённым на сервере, **Когда** приходит соответствующая ошибка синхронизации, **Тогда** рецепт убирается из активного списка на iOS

---

### Краевые случаи

- Одновременное редактирование одного рецепта на iOS и вебе — итог сходится без ручного merge
- Отправка обновления при разорванном socket до получения `sync_confirmed`
- Переполнение или сбой очереди офлайн-операций при длительном офлайне
- Редактирование рецепта, документ которого ещё не загружен с сервера (только метаданные в коллекции)
- Смена аккаунта с неотправленной очередью — очередь не должна «перетечь» в другой userId
- Попытка редактировать рецепт v1/v2 — UI остаётся read-only; мутации Y.Doc не выполняются
- Попытка редактировать описание (XmlFragment v3) — вне scope Phase 3; UI не предлагает rich-text редактор (описание только чтение даже для v3, если отображается)
- Создание нового рецепта или удаление из коллекции — вне scope Phase 3

## Требования *(mandatory)*

### Функциональные требования

- **FR-001**: Приложение ДОЛЖНО записывать изменения в документ рецепта `{userId}:recipe:{recipeId}` через мутации Y.Doc (write-транзакции yrs), а не через REST для тела рецепта
- **FR-002**: Приложение ДОЛЖНО отправлять локальные обновления на сервер событием `sync_request` с бинарным `yjsUpdate` и `lastSyncedAt`, в том же формате, что веб-клиент
- **FR-003**: Приложение ДОЛЖНО применять debounce ~1 секунды перед отправкой, объединяя накопленные локальные обновления в один пакет (как `yjs-client.ts`)
- **FR-004**: Для рецептов **v3** пользователь ДОЛЖЕН иметь возможность редактировать поля `name`, `servings`, `color` в `Y.Map('recipe')`; для **v1/v2** — запрещено
- **FR-005**: Для рецептов **v3** пользователь ДОЛЖЕН иметь возможность выполнять CRUD ингредиентов через `Y.Array` of `Y.Map` (`id`, `name`, `amount`, `originalAmount`, `order`); для **v1/v2** — только чтение
- **FR-006**: Для рецептов **v3** пользователь ДОЛЖЕН иметь возможность редактировать `nutrition` как `Y.Map` (или эквивалент v3); для **v1/v2** — только чтение
- **FR-006a**: При `version` v1 или v2 приложение ДОЛЖНО показывать баннер «устаревший формат, только чтение» и НЕ ДОЛЖНО вызывать write-транзакции и `sync_request` для этого документа
- **FR-007**: Приложение НЕ ДОЛЖНО сохранять UI-множитель порций (`scaleFactor` слайдера) в Y.Doc — только `servings` и данные ингредиентов, как на вебе
- **FR-008**: Приложение ДОЛЖНО ставить неотправленные `sync_request` в офлайн-очередь SQLite при отсутствии соединения и отправлять очередь FIFO (с merge обновлений одного документа где возможно) после reconnect
- **FR-009**: Приложение ДОЛЖНО обновлять локальный снимок Y.Doc в SQLite после успешной отправки или подтверждения (`sync_confirmed`), сохраняя актуальный `lastSyncedAt`
- **FR-010**: Приложение ДОЛЖНО продолжать принимать `recipe_updated` / `collection_updated` с сервера и сливать их с локальными правками через CRDT
- **FR-011**: Приложение ДОЛЖНО обрабатывать `sync_error` при записи: ownership failure, tombstone/deleted recipe, invalid update — с локализованными сообщениями и без падения
- **FR-012**: Приложение ДОЛЖНО показывать пользователю состояние сохранения: «сохранено локально», «синхронизация…», «синхронизировано», «ошибка» — через i18n
- **FR-013**: Редактирование описания рецепта (Y.Text / XmlFragment) и шагов с rich-text — вне scope; только plain-поля и ингредиенты/nutrition
- **FR-014**: Мутации коллекции (добавление/удаление рецепта из списка, pin) и список покупок — вне scope Phase 3
- **FR-015**: Изменения с iOS ДОЛЖНЫ оставаться бинарно совместимыми с Yjs 13.6.30 и схемой `docs/YJS-SCHEMA.md`

### Ключевые сущности

- **Локальная мутация**: Изменение в Y.Doc, зафиксированное write-транзакцией yrs до отправки на сервер.
- **Очередь офлайн-операций**: Упорядоченный набор отложенных бинарных обновлений по ключу документа с метаданными времени и статусом отправки.
- **Состояние синхронизации записи**: Per-recipe индикатор для UI (ожидание, в полёте, подтверждено, ошибка).
- **Данные рецепта (запись)**: Те же сущности, что в Phase 2 (`RecipeData`, `IngredientData`, `NutritionData`), но с путями записи в Y.Map / Y.Array.

## Критерии успеха *(mandatory)*

### Измеримые результаты

- **SC-001**: Пользователь меняет название или порции на iOS — веб-клиент показывает те же значения в течение 5 секунд при стабильной сети
- **SC-002**: Пользователь добавляет или удаляет ингредиент на iOS — состав на вебе совпадает по id, имени, количеству и порядку в течение 5 секунд
- **SC-003**: После редактирования в авиарежиме и восстановления сети изменения появляются на вебе в течение 10 секунд без повторного действия пользователя
- **SC-004**: При быстром вводе 5 полей подряд на сервер уходит не более 2 отдельных `sync_request` за 10 секунд (debounce работает)
- **SC-005**: Одновременное редактирование **v3**-рецепта на iOS и вебе завершается согласованным состоянием без потери данных в 95% ручных прогонов (без ручного merge)
- **SC-007**: Для рецепта v1/v2 пользователь не может сохранить изменение с iOS; баннер отображается при каждом открытии до миграции в v3 через веб
- **SC-006**: При `sync_error` (ownership / deleted) пользователь видит понятное сообщение на родном языке (ru/en) в течение 1 секунды после ответа сервера

## Допущения

- Phase 2 полностью развёрнута: чтение v1/v2/v3 остаётся; Phase 3 добавляет запись **только v3**
- Миграция v1/v2 → v3 выполняется в веб-клиенте; iOS не реализует миграцию документов
- Web → iOS синхронизация уже проверена пользователем; Phase 3 валидирует обратное направление
- Бэкенд и веб-клиент не меняются; протокол — существующие события Socket.IO
- Редактирование описания переносится на Phase 4 (WKWebView + Tiptap)
- Создание нового рецепта и удаление из коллекции — Phase 5 или позже
- `scaleFactor` остаётся локальным UI-состоянием слайдера, не полем Y.Doc
- Пользователь редактирует только свои рецепты (ownership проверяет сервер)
- Тестирование bidirectional sync выполняется парой iOS + веб на одном userId

## Вне scope (явно)

- Rich-text / XmlFragment описание (Phase 4)
- Список покупок, pin, создание/удаление рецепта в коллекции (Phase 5)
- Загрузка изображений рецепта (остаётся REST, как в Phase 2)
- PDF, импорт URL, виджеты
- Запись/миграция рецептов v1/v2 на iOS
- Детальные макеты и wireframes (отдельный артефакт `plan.md` / design, см. раздел «Пользовательский интерфейс»)
