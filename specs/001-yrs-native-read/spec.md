# Спецификация функции: Интеграция yrs и нативное чтение

**Feature Branch**: `001-yrs-native-read`

**Created**: 2026-06-01

**Status**: ✅ Done (аудит кода 2026-06-15)

**Input**: Фаза 2 Recipe Scaler Native — интеграция yrs CRDT-движка, создание YjsSyncService, замена чтения рецептов через REST API на нативное чтение из Y.Doc. Фундаментальная фаза, которая открывает путь к редактированию и полной синхронизации.

## Пользовательские сценарии и тестирование *(mandatory)*

### Пользовательская история 1 — Просмотр списка рецептов из Y.Doc (Приоритет: P1)

Пользователь открывает приложение и видит свою коллекцию рецептов, загруженную из CRDT Y.Doc вместо REST API. Список выглядит идентично Фазе 1, но данные проходят через yrs-движок и синхронизацию Socket.IO.

**Обоснование приоритета**: Это фундаментальный путь данных — все остальные функции зависят от способности приложения читать данные коллекции из Y.Doc. Без этого невозможны ни редактирование, ни синхронизация в реальном времени.

**Независимое тестирование**: Можно полностью протестировать, войдя в аккаунт, просмотрев список рецептов и убедившись, что отображаются те же рецепты, что и в веб-клиенте. Создаёт ценность, выстраивая сквозной конвейер данных CRDT.

**Сценарии приёмки**:

1. **Если** пользователь авторизован и имеет рецепты в коллекции, **Когда** он открывает приложение, **Тогда** список рецептов отображает все неудалённые рецепты из документа коллекции Y.Doc с корректными названием, цветом, изображением и статусом закрепления
2. **Если** приложение подключено к сети, **Когда** другое устройство изменяет коллекцию (добавляет, удаляет или меняет порядок рецептов), **Тогда** список обновляется в реальном времени в течение 2 секунд через Socket.IO broadcast
3. **Если** приложение ранее было подключено, **Когда** пользователь повторно открывает приложение, **Тогда** список рецептов мгновенно загружается из локального снимка SQLite, а синхронизация с сервером происходит в фоновом режиме
4. **Если** у рецепта в `name` есть ведущее эмодзи, **Когда** пользователь смотрит список, **Тогда** слева отображается это эмодзи, а в тексте строки — название без ведущего эмодзи; если эмодзи нет — слева цветной кружок `color` (как в мобильном `recipe-list.tsx`)
5. **Если** в коллекции есть закреплённые рецепты, **Когда** пользователь смотрит список, **Тогда** сначала секция «Закрепленные», затем (при наличии незакреплённых) секция «Рецепты»; порядок внутри секции совпадает с веб-клиентом
6. **Если** два рецепта отличаются только ведущим эмодзи в `name`, **Когда** пользователь смотрит список, **Тогда** они сортируются рядом по отображаемому названию (эмодзи не участвует в сравнении)

**Эталон UI (мобильная веб-версия)**: `recipe-scaler-web/recipe-scaler/src/pages/recipe-list.tsx`, утилита `shared/utils/recipe-title-emoji.ts`, сортировка `sortCollectionsByDisplayName` в `use-yjs-sync.ts`.

### Пользовательская история 2 — Просмотр деталей рецепта из Y.Doc (Приоритет: P2)

Пользователь нажимает на рецепт в списке и видит его полные детали (название, порции, ингредиенты, питание), прочитанные из документа рецепта Y.Doc через yrs, заменяя предыдущий просмотр деталей на основе REST.

**Обоснование приоритета**: Детали рецепта — вторая по важности view. Как только коллекция читается из Y.Doc, отдельные документы рецептов также должны читаться из Y.Doc для обеспечения целостности данных и подготовки к нативному редактированию.

**Независимое тестирование**: Можно полностью протестировать, нажав на любой рецепт в списке и проверив, что все поля совпадают с веб-клиентом, включая ингредиенты с правильными количествами и порядком.

**Сценарии приёмки**:

1. **Если** рецепт существует в коллекции, **Когда** пользователь нажимает на него, **Тогда** отображаются название, порции, ингредиенты, питание и все метаданные, прочитанные из Y.Doc рецепта
2. **Если** пользователь просматривает детали рецепта, **Когда** другое устройство редактирует этот рецепт, **Тогда** детали обновляются в реальном времени в течение 2 секунд
3. **Если** рецепт был ранее загружен, **Когда** пользователь просматривает его в офлайне, **Тогда** детали загружаются из локального снимка SQLite

---

### Пользовательская история 3 — Масштабирование рецепта через Y.Doc (Приоритет: P3)

Пользователь регулирует слайдер размера порций рецепта и видит, что количества ингредиентов масштабируются корректно, с чтением базовых количеств из данных ингредиентов Y.Doc.

**Обоснование приоритета**: Масштабирование — ключевая функция Recipe Scaler. Подтверждает, что данные ингредиентов корректно читаются из структуры Y.Doc, и существующий UI слайдера Фазы 1 продолжает работать с новым источником данных.

**Независимое тестирование**: Можно полностью протестировать, открыв рецепт, изменив слайдер порций и убедившись, что количества ингредиентов масштабируются пропорционально на основе значения порций в Y.Doc.

**Сценарии приёмки**:

1. **Если** рецепт имеет 4 порции и ингредиенты с количествами, **Когда** пользователь переводит слайдер на 8 порций, **Тогда** все количества ингредиентов удваиваются на основе поля `originalAmount`
2. **Если** отображаются масштабированные ингредиенты, **Когда** пользователь возвращает слайдер к исходному количеству порций, **Тогда** все количества возвращаются к исходным значениям
3. **Если** рецепт v1 с ингредиентами в виде JSON-строки, **Когда** пользователь просматривает и масштабирует его, **Тогда** ингредиенты корректно парсятся и масштабируются (обратная совместимость)

---

### Пользовательская история 4 — Жизненный цикл подключения синхронизации (Приоритет: P4)

Приложение пользователя поддерживает постоянное Socket.IO подключение к бэкенду, авторизуется с учётными данными пользователя и автоматически переподключается при потере и восстановлении связи.

**Обоснование приоритета**: Надёжное подключение синхронизации — фундамент для всех функций реального времени. Пользователям нужно, чтобы их данные оставались актуальными без ручных действий.

**Независимое тестирование**: Можно протестировать, войдя в систему, переключившись в авиарежим, затем вернувшись в сеть — рецепты должны обновиться автоматически без действий пользователя.

**Сценарии приёмки**:

1. **Если** пользователь входит со своей seed-фразой, **Когда** приложение запускается, **Тогда** оно авторизуется через Socket.IO с userId и deviceId и получает подтверждение
2. **Если** приложение подключено, **Когда** сеть пропадает, **Тогда** приложение показывает индикатор офлайна, но остаётся полностью функциональным с локальными данными
3. **Если** приложение офлайн, **Когда** сеть восстанавливается, **Тогда** приложение переподключается в течение 5 секунд, повторно авторизуется и синхронизирует все отложенные изменения

---

### Пользовательская история 5 — Локальное сохранение состояния Y.Doc (Приоритет: P5)

Данные рецептов пользователя сохраняются локально, чтобы приложение загружалось мгновенно при повторном открытии, даже без сети.

**Обоснование приоритета**: Быстрый запуск и офлайн-доступ — ключевые составляющие мобильного опыта. Локальное сохранение обеспечивает сохранность состояния Y.Doc между перезапусками приложения.

**Независимое тестирование**: Можно протестировать, загрузив рецепты, принудительно закрыв приложение, повторно открыв его в авиарежиме и убедившись, что все рецепты по-прежнему видны.

**Сценарии приёмки**:

1. **Если** рецепты были загружены и синхронизированы, **Когда** пользователь принудительно закрывает и снова открывает приложение, **Тогда** список рецептов появляется мгновенно из SQLite без ожидания сети
2. **Если** рецепт был полностью загружен (детали просмотрены), **Когда** пользователь повторно открывает приложение в офлайне, **Тогда** детали рецепта, включая все ингредиенты, доступны из локального хранилища
3. **Если** произошло несколько циклов синхронизации, **Когда** приложение открывается заново, **Тогда** загружается самое свежее синхронизированное состояние (без устаревших данных от предыдущих сессий)

### Краевые случаи

- Что произойдёт, когда бинарное состояние Y.Doc с сервера повреждено или не может быть разобрано yrs?
- Как приложение обрабатывает рецепт, который существует в коллекции, но документ рецепта которого не удалось загрузить?
- Что произойдёт, если Socket.IO отправит `sync_error` во время начальной загрузки документа?
- Как приложение обрабатывает рецепты v1, где ингредиенты — JSON-строка вместо Y.Array?
- Что произойдёт при переключении аккаунта — будут ли очищены все экземпляры Y.Doc и локальные снимки?
- Как ведёт себя приложение, когда XCFramework yrs не может инициализироваться (например, несовпадение архитектуры)?
- Что произойдёт, если придут два быстрых события `collection_updated` — будут ли они корректно объединены?

## Требования *(mandatory)*

### Функциональные требования

- **FR-001**: Приложение ДОЛЖНО компилировать yrs как XCFramework (Rust → C FFI → Swift) с поддержкой arm64 (устройство), x86_64 (симулятор) и arm64 (симулятор на Apple Silicon)
- **FR-002**: Приложение ДОЛЖНО предоставить Swift-обёртку над yrs C API (yffi), обеспечивающую жизненный цикл документов, доступ к разделяемым типам и операции синхронизации
- **FR-003**: Приложение ДОЛЖНО реализовать YjsSyncService, который подключается к бэкенду через Socket.IO, используя те же события, что и веб-клиент (`auth`, `load_document`, `sync_request`, `document_loaded`, `collection_updated`, `recipe_updated`)
- **FR-004**: Приложение ДОЛЖНО создавать и управлять экземплярами Y.Doc для документов коллекции и рецептов, используя ключи документов, соответствующие веб-клиенту (`{userId}:collection`, `{userId}:recipe:{recipeId}`)
- **FR-005**: Приложение ДОЛЖНО читать `Y.Array('recipes')` документа коллекции и отображать список рецептов с названием, цветом, imageUrl, статусом закрепления, исключая удалённые записи (tombstone)
- **FR-006**: Приложение ДОЛЖНО читать `Y.Map('recipe')` документов рецептов и отображать детали рецепта: название, порции, цвет, ингредиенты, питание и метаданные
- **FR-007**: Приложение ДОЛЖНО обрабатывать все три версии рецептов (v1, v2, v3) при чтении: ингредиенты v1 как JSON-строку, v2/v3 как Y.Array; описание v1/v2 как string/Y.Text, v3 как XmlFragment
- **FR-008**: Приложение ДОЛЖНО сохранять снимки состояния Y.Doc в SQLite с отслеживанием `lastSyncedAt` для каждого документа
- **FR-009**: Приложение ДОЛЖНО загружать документы из SQLite при запуске для мгновенного отображения, затем синхронизировать с сервером в фоновом режиме
- **FR-010**: Приложение ДОЛЖНО применять удалённые обновления, полученные через Socket.IO broadcast (`recipe_updated`, `collection_updated`), к соответствующим экземплярам Y.Doc
- **FR-011**: Приложение ДОЛЖНО реактивно обновлять SwiftUI-views при изменении данных Y.Doc через наблюдателей yrs
- **FR-012**: Приложение ДОЛЖНО авторизоваться на бэкенде, используя существующую seed-авторизацию (BIP39 + Keychain), и отправлять событие `auth` с userId и deviceId
- **FR-013**: Приложение ДОЛЖНО обрабатывать жизненный цикл Socket.IO-подключения: автоматическое переподключение при разрыве, повторная авторизация после переподключения, перезагрузка устаревших документов
- **FR-014**: Приложение ДОЛЖНО отображать индикатор подключения офлайн/онлайн, отражающий состояние Socket.IO-соединения
- **FR-015**: Приложение ДОЛЖНО обрабатывать события `sync_error` от сервера без падения — показывать понятную ошибку для ошибок владения, удалять удалённые рецепты из локального списка
- **FR-016**: Приложение ДОЛЖНО мигрировать список рецептов с источника данных REST API на источник данных Y.Doc, устранив зависимость от REST для чтения рецептов
- **FR-017**: Приложение ДОЛЖНО сохранять функциональность масштабирования ингредиентов, используя поля `originalAmount` и `servings` из данных Y.Doc
- **FR-018**: Приложение ДОЛЖНО точно соблюдать схему Y.Doc, задокументированную в `docs/YJS-SCHEMA.md` — ключи документов, разделяемые типы и имена полей должны совпадать для бинарной совместимости

#### Список рецептов — паритет с мобильным веб-клиентом

- **FR-019 (интерлиньяж и метрики строки)**: Строка списка ДОЛЖНА визуально соответствовать мобильной веб-строке `RecipeListItem`: минимальная высота **44 pt**; вертикальные отступы контента **10 pt** (`py-2.5`); размер шрифта названия **16 pt** (`text-base` / `font-sans`); при переносе названия на две строки — увеличенный межстрочный интервал (≈ **8 pt** `lineSpacing`, эквивалент ~1.5 line-height); выравнивание маркера и текста по **верхнему** краю (`items-start`); превью `imageUrl` — **44×44 pt**, `object-cover`, справа в строке
- **FR-020 (ведущее эмодзи)**: Логика ведущего эмодзи ДОЛЖНА совпадать с `shared/utils/recipe-title-emoji.ts`: распознавание одного ведущего emoji-последовательности (включая ZWJ, флаги, keycap) после необязательных пробелов в начале `name`; в UI слева — эмодзи **18 pt** в колонке **12 pt** (с небольшим смещением как на вебе), иначе — кружок цвета **12×12 pt** (`color`, fallback `oklch(0.65 0.25 270)`); в тексте строки — `getTitleWithoutLeadingEmoji(name)` (пустое → локализованное «Без названия»); эмодзи в середине/конце названия не извлекается и не скрывается
- **FR-021 (сортировка и секции pin)**: Список ДОЛЖЕН сортироваться как `sortCollectionsByDisplayName` в веб `use-yjs-sync.ts`: (1) все `isPinned == true` выше остальных; (2) внутри группы — `compareRecipeNamesIgnoringLeadingEmoji` по display name (`localeCompare`, `sensitivity: base`); (3) при равенстве display name — сравнение полного `name`; (4) при равенстве имён — `id` (`localeCompare`). В UI закреплённые и незакреплённые ДОЛЖНЫ быть в **отдельных секциях** с заголовками `recipes.section-pinned` / `recipes.section-unpinned` (заголовок «Рецепты» только если есть и закреплённые, и незакреплённые); inline-иконка pin в строке не требуется (pin только через заголовок секции, как на вебе)

**Реализация (iOS, 2026-06-02)**: `RecipeScalerNative/Utils/RecipeTitleEmoji.swift`, `RecipeListView.swift`, `CollectionEntry.sorted` → `RecipeTitleEmoji.sortCollectionEntries`.

### Ключевые сущности

- **Y.Doc**: Экземпляр CRDT-документа, управляемый yrs. Три типа: коллекция, рецепт, список покупок. Идентифицируется ключом документа (`{userId}:collection`, `{userId}:recipe:{recipeId}`).
- **YjsSyncService**: Центральный Swift-сервис, управляющий жизненным циклом Y.Doc, Socket.IO-подключением, протоколом синхронизации и офлайн-сохранением. Отражает `yjs-client.ts` из веб-приложения.
- **Снимок Y.Doc**: Локальная запись SQLite, содержащая бинарное состояние (`Data`) и временную метку `lastSyncedAt` для каждого ключа документа.
- **Запись коллекции**: `Y.Map` внутри `Y.Array('recipes')` коллекции, содержащая метаданные рецепта: id, name, color, imageUrl, updatedAt, deleted (tombstone), isPinned.
- **Данные рецепта**: `Y.Map('recipe')` внутри документа рецепта, содержащая: name, servings, scaleFactor, color, ingredients (Y.Array или JSON-строка), nutrition (Y.Map или JSON), version, временные метки и другие метаданные.

## Критерии успеха *(mandatory)*

### Измеримые результаты

- **SC-001**: Пользователи видят список рецептов в течение 2 секунд после открытия приложения, с загрузкой из локального SQLite и последующей фоновой синхронизацией с сервером
- **SC-002**: Список рецептов и детали отображают идентичные данные с веб-клиентом при просмотре одного и того же аккаунта (включая порядок строк, секции pin, отображение ведущего эмодзи и метрики строки по FR-019–FR-021)
- **SC-003**: Обновления в реальном времени с других устройств появляются на iOS в течение 3 секунд после внесения изменений
- **SC-004**: Приложение остаётся полностью функциональным в офлайне — все ранее загруженные рецепты доступны из локального хранилища
- **SC-005**: Масштабирование ингредиентов даёт математически корректные результаты для всех версий рецептов (v1, v2, v3)
- **SC-006**: Socket.IO переподключается в течение 5 секунд после восстановления сети без вмешательства пользователя
- **SC-007**: Все операции с Y.Doc сохраняют бинарную совместимость с Yjs 13.6.30 на сервере — без повреждения данных или ошибок синхронизации из-за несовпадения протокола

## Допущения

- Существующий Socket.IO бэкенд работает и не изменяется — модификации бэкенда для iOS не требуются
- Пользователи уже создали аккаунты через веб-клиент и могут авторизоваться своей seed-фразой
- yrs C API (yffi) предоставляет достаточный охват для жизненного цикла документов, доступа к разделяемым типам, регистрации наблюдателей и кодирования/декодирования бинарных обновлений
- Доступны Mac на Apple Silicon для сборки XCFramework для arm64-симулятора
- SwiftData (уже используется в Фазе 1) может быть расширена или заменена на GRDB для SQLite-хранения снимков Y.Doc
