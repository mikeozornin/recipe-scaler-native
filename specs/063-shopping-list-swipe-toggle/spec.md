# Спецификация: свайп от левого края для отметки покупки

**Ветка**: `063-shopping-list-swipe-toggle`
**Дата**: 2026-08-12
**Статус**: Draft
**Вводная**: пользователь хочет свайпом от левого края отмечать пункт списка покупок как купленный (и снимать отметку). Иногда проще свайпнуть, чем целиться в галочку.
**Зависимости**: `024-shopping-list-completion` (каноническая реализация списка покупок — `ShoppingListView`, swipe-delete уже существует).

---

## Границы (Scope)

**Входит:**

- Жест swipe-to-toggle от leading-края в строке списка покупок — для уже купленных и некупленных пунктов.
- Действие **переключает** состояние `checked` (mark/unmark), как тап по чекбоксу.
- Поведение жеста по порогу: **полный свайп через весь ряд** автоматически коммитит toggle; **частичный свайп** только раскрывает зелёную кнопку-индикатор и требует второго тапа для коммита (стандартное поведение SwiftUI `.swipeActions`, паритет с Mail/Reminders).
- Визуальная метка действия — зелёная галочка (Apple Reminders-стиль), видна и при partial reveal, и при full swipe.
- Свайп доступен в обеих секциях списка: «Купить» и «Куплено».
- Параллельно сохраняется существующий trailing swipe-delete (из спеки 024).

**Не входит (out of scope):**

- Изменение схемы Y.Doc, новых sync-событий, новых публичных API — мутация переиспользует существующий путь записи (`checked` в `Y.Map('shopping')`).
- Изменение behaviour существующего tap-to-check, swipe-to-delete, inline edit, add-from-recipe.
- Confetti/анимации сверх уже зафиксированных в 024 (staging ~1 с + haptic).
- Списки на вебе, public share-страница, rich-text — не затрагиваются.
- Жесты в иных списках приложения (таймеры, рецепты).

## Пользовательские сценарии и тестирование *(обязательно)*

### User Story 1 — Отметить покупку свайпом слева (P1)

Пользователь ведёт список покупок в магазине. Пункт «Молоко 1 л» отображается в секции «Купить». Вместо точного тапа по небольшому чекбоксу пользователь свайпает строку от левого края — пункт переходит в секцию «Куплено» с зелёной галочкой действия и привычным staging+haptic из 024.

**Почему приоритет**: основной сценарий, ради которого заведена фича — снизить промахи мимо чекбокса одной рукой.

**Независимое тестирование**: открыть вкладку Shopping с непустым списком «Купить», свайпнуть строку влево-от-края, убедиться, что пункт переехал в «Куплено».

**Acceptance Scenarios**:

1. **Given** в секции «Купить» есть пункт P (unchecked), **When** пользователь выполняет полный leading swipe через весь ряд, **Then** действие показывается зелёной галочкой и после завершения жеста P становится checked и переезжает в секцию «Куплено».
2. **Given** в секции «Купить» есть пункт P (unchecked), **When** пользователь выполняет частичный leading swipe, **Then** показывается зелёная кнопка-индикатор, P не меняет состояние до тех пор, пока пользователь не тапнет по индикатору.
3. **Given** включён staging-check с haptic (см. 024 US-P1), **When** свайп закоммичен (full swipe или тап по reveal-кнопке), **Then** срабатывает тот же haptic и та же пауза staging, что и при тапе по чекбоксу.
4. **Given** устройство офлайн, **When** выполнен leading swipe, **Then** локальное состояние меняется, мутация попадает в offline-очередь и будет отправлена после реконнекта (паритет с tap-to-check из 024).

---

### User Story 2 — Вернуть покупку в «Купить» свайпом слева (P2)

В секции «Куплено» пользователь случайно отметил не тот пункт. Свайпом от левого края по строке в «Куплено» он снимает отметку — пункт возвращается в «Купить».

**Почему приоритет**: создаёт симметрию «toggle», без неё жест был бы односторонним и требовал бы точного тапа по чекбоксу для отката.

**Независимое тестирование**: отметить любой пункт свайпом/тапом, перейти в секцию «Куплено», свайпнуть строку от левого края — пункт возвращается в «Купить».

**Acceptance Scenarios**:

1. **Given** пункт P находится в секции «Куплено» (checked), **When** выполнен leading swipe по P, **Then** действие показывается зелёной галочкой, P становится unchecked и переезжает в секцию «Купить».
2. **Given** у пользователя есть купленные пункты P1 и P2, **When** свайп applies только к P1, **Then** P2 остаётся в «Куплено», меняется только P1.

---

### User Story 3 — Свайп-удаление и leading toggle не конфликтуют (P3)

В списке уже существует trailing swipe-delete (024). Новый leading swipe-toggle должен сосуществовать с ним: жесты не мешают друг другу, пользователь может выбрать любой из двух для своего сценария.

**Почему приоритет**: регрессионная защита — нужно явно зафиксировать, что новый жест не ломает удаление и не подменяет его.

**Независимое тестирование**: на одной строке выполнить leading swipe (toggle), затем trailing swipe (delete) — оба должны работать как раньше.

**Acceptance Scenarios**:

1. **Given** строка P с обоими жестами настроена, **When** пользователь делает leading swipe, **Then** показывается только toggle-действие; trailing swipe-delete при этом не активируется одновременно.
2. **Given** строка P, **When** пользователь делает trailing swipe (справа), **Then** показывается delete-действие из 024; leading-toggle при этом не активируется.
3. **Given** пользователь отменил swipe, отпустив палец ниже порога, **Then** строка возвращается в исходное положение без мутации состояния.

---

### Edge Cases

- **Пустой список**: ведущих строк нет — жест неприменим; пустые состояния из 024 не меняются.
- **Ручной пункт** (без recipeId): leading toggle должен работать одинаково с ингредиентными — мутация `checked` идентична.
- **Inline edit активен** для ручного пункта: пока строка в режиме редактирования, swipe-действие не должно мешать вводу (см. паритет с 024 US-L4).
- **Быстрые повторные свайпы** по одной строке до drain sync: всё корректно, т.к. путь мутации и offline-очередь уже реализованы в 024.
- **Свайп прерван ниже порога reveal/commit** (палец отпущен до того, как показана кнопка-индикатор, или до достижения полного свайпа): строка анимацией возвращается в исходное положение без мутации состояния; конфликт с trailing swipe-delete не активируется.
- **Пользователь передумал в середине жеста** (палец ушёл к reveal и вернулся в исходную позицию до отпускания): действует стандартное SwiftUI-поведение — жест отменяется, мутации нет, строка возвращается в исходное положение.
- **VoiceOver / Switch Control / Voice Control**: leading swipe — это прямой манипулятивный жест; существующий a11y-путь отметки через tap по чекбоксу должен оставаться (свайп не заменяет доступность). Чекбокс и swipe-действие ДОЛЖНЫ озвучиваться одинаковыми ключами `shopping.action.mark-purchased` / `shopping.action.unmark-purchased` (см. FR-011), чтобы a11y-пользователь получал согласованное описание отметки покупки независимо от способа ввода.

## Требования *(обязательно)*

### Конституционная проверка

- **I. CRDT-First** ✅ — мутация состояния `checked` переиспользует существующий Y.Doc путь из 024; новых полей/коллекций нет.
- **II. Web Parity** ✅ — это iOS-only UX-ускорение ввода; веб продолжает работать через чекбокс, схема и события не меняются.
- **III. Offline-First** ✅ — мутация идёт через ту же offline-очередь, что и tap-to-check.
- **IV. Native UI, Minimal WebView** ✅ — жест реализуется в SwiftUI-строке списка, не в WebView.
- **V. Phased, Independently Testable Delivery** ✅ — фича доставляет самостоятельную ценность (ускорение отметки) и не тянет за собой работы из более поздних фаз.

### Функциональные требования

- **FR-001**: Пользователь ДОЛЖЕН иметь возможность отметить пункт списка покупок купленным свайпом от левого края строки.
- **FR-002**: Пользователь ДОЛЖЕН иметь возможность снять отметку «куплено» тем же жестом в секции «Куплено» (toggle-семантика).
- **FR-003**: Система ДОЛЖНА показывать во время жеста индикатор действия в виде зелёной галочки (Apple Reminders-стиль, system green).
- **FR-004**: Жест ДОЛЖЕН быть доступен в обеих секциях — «Купить» и «Куплено».
- **FR-005**: Система НЕ ДОЛЖНА ломать существующий trailing swipe-delete из 024; два жеста должны сосуществовать на одной строке.
- **FR-006**: Система ДОЛЖНА применять тот же путь мутации состояния (Y.Doc `checked`), staging-check (~1 с) и haptic, что и tap-to-check из 024, без дублирования логики.
- **FR-007**: Мутация ДОЛЖНА корректно ставиться в offline-очередь и дрейниться при реконнекте (паритет с tap-to-check).
- **FR-008**: Если строка в режиме inline edit (024 US-L4), leading swipe ДОЛЖЕН быть подавлён, чтобы не мешать вводу текста.
- **FR-009**: Все пользовательские строки интерфейса (labels действий, accessibility-описания) ДОЛЖНЫ браться из `RecipeScalerNative/Resources/Localizable.xcstrings` — без хардкода. Для нового жеста заводятся **два отдельных ключа**: `shopping.action.mark-purchased` (для unchecked → checked) и `shopping.action.unmark-purchased` (для checked → unchecked). Действие выбирается по текущему состоянию пункта.
- **FR-010**: Полный свайп от leading-края через весь ряд ДОЛЖЕН автоматически коммитить toggle; частичный свайп ДОЛЖЕН только reveal кнопку-индикатор и требовать второго тапа для коммита (стандартное поведение SwiftUI `.swipeActions`).
- **FR-011**: Accessibility существующего tap-to-check чекбокса в `ShoppingListView` ДОЛЖНО быть приведено к тем же ключам `shopping.action.mark-purchased` / `shopping.action.unmark-purchased`, что и новый жест, чтобы a11y-описание отметки покупки было единым по всему экрану.

### Ключевые сущности

Сущности не вводятся — используются существующие из 024:

- **Shopping item** (`Y.Map('shopping')` item): атрибут `checked` (bool) мутирует, остальные атрибуты без изменений.
- **Shopping list view state**: секции «Купить» / «Куплено» — структура без изменений.

## Downstream consumers

- **`ShoppingListView` и её row-компонент** — место внедрения жеста; влияет на всех пользователей вкладки Shopping.
- **`DocumentManager+ShoppingList` / sync-слой** — без изменений, но должен быть вызван по тому же пути, что и tap-to-check (важно для планирования — переиспользовать, а не дублировать).
- **Тесты и verify-скрипты 024** (`verify-shopping-list*.sh`) — должны оставаться зелёными; скорее всего потребуется точечное расширение smoke/UI-polish проверки на ведущий жест.
- **Accessibility** — VoiceOver/Hover/switch-пользователи продолжат пользоваться чекбоксом; новый жест — это бонус для пользователей без a11y-потребностей, не замена. В рамках фичи (FR-011) существующий чекбокс приводится к тем же a11y-ключам, что и swipe-действие — это минимальный cleanup, без переделки всей accessibility-модели экрана.

## Positive invariants

- Веб-клиент и публичная share-страница не должны заметить изменение — sync-контракт неизменен.
- Если новый жест временно отключён/сломан, вся функциональность списка покупок из 024 продолжает работать через tap-to-check.
- Состояние списка покупок на устройстве A после swipe должно совпадать с состоянием после аналогичного tap (мутация идентична).
- Trailing swipe-delete продолжает работать идентично 024.

---

## Async lifecycle / Teardown

- Жест — чисто UI-событие, не создаёт фоновых задач, таймеров, подписок, соединений.
- Все ресурсные обязанности (sync-отправка, offline-queue drain, haptic, staging-таймер) уже принадлежат существующему слою мутации 024 и переиспользуются как есть.
- Новых `Task {}`, observer'ов, Combine-подписок, gesturerecognizer-ов вне SwiftUI-декларативного API заводить не планируется (план уточнит детали).
- Teardown при уходе со экрана Shopping — без изменений по сравнению с 024.

## Критерии успеха *(обязательно)*

### Измеримые исходы

- **SC-001**: Пользователь может отметить любой пункт списка покупок купленным ведущим свайпом в ≤ 1 жест (без необходимости точно попасть в чекбокс).
- **SC-002**: Действие toggle доступно в обеих секциях («Купить» и «Куплено»); пользователь может снять отметку тем же жестом.
- **SC-003**: Существующий trailing swipe-delete и tap-to-check из 024 сохраняют 100% своей функциональности — нет регрессий.
- **SC-004**: В офлайн-режиме swipe-toggle ставит мутацию в очередь так же надёжно, как tap-to-check — после реконнекта состояние сходится с вебом (паритет 024 SC-001/SC-002).
- **SC-005**: Все пользовательские строки нового UI (accessibility label действия жеста) локализованы через `Localizable.xcstrings`; `lint-i18n.sh` проходит без новых предупреждений.
- **SC-006**: Build `xcodebuild -scheme RecipeScalerNative build` зелёный; существующие `verify-shopping-list*.sh` зелёные; `verify-shopping-list-ui-polish.sh` расширен точечным блоком assert-ов на leading swipe (toggle коммит, зелёный индикатор, отсутствие конфликта с trailing delete, отмена жеста ниже порога). Отдельных verify-скриптов под фичу не заводится.

## Допущения

- Базовый компонент строки списка покупок (`ShoppingListView` row) уже реализован на SwiftUI и допускает декларативную настройку `.swipeActions(edge:)` — план проверит и зафиксирует точный вид API/компонента.
- staging-check (~1 с) и haptic из 024 — общая функция/вызов; план переиспользует её, а не клонирует.
- Используется системный `Color.green` (или семантический equivalent app accent) для галочки; конкретный токен зафиксирует план/UI-аудит.
- Существующие verify-скрипты достаточно расширяемы, чтобы добавить assertion на ведущий жест без их переписывания.
- На момент написания спеки в проекте нет отдельной layout-задачи под Figma (меняется только поведение строки, не вёрстка экрана); `layout.md`/`layout-audit.json` по плану не требуются — план зафиксирует это явно (если layout всё же понадобится, дверь открыта).
- На строках с inline-edit режимом жест подавляется — это допущение закреплено в FR-008.
