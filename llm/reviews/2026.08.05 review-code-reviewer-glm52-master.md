### High

#### 1. **[Business Logic / Performance / Security]** `DeepLinkRouter.lastHandledURL` permanently blocks legitimate re-taps of the same Universal Link

- **Impact**: After iOS delivers a UL (e.g. `https://recipe-scaler.ru/recipe/<id>`) and the user backs out and taps the **same** link again from Safari, the second delivery is silently dropped because the URL equals the static `lastHandledURL`. The user must tap a *different* link (or kill the app) to route again. Most user-visible on repeated `recipe/`, `public/@/…` taps — exactly the spec-059 use case.
- **Root cause**: `lastHandledURL: URL?` is set on every parse but never reset (only `_resetLastHandledURLForTesting()` clears it). The iOS double-delivery race it's meant to suppress happens within milliseconds; legitimate re-taps happens seconds-to-minutes later — both look identical to this guard.
- **Recommendation**: Clear `lastHandledURL` inside `DeepLinkRouter.clear()` (so each consume cycle frees the dedup slot), OR replace with a short TTL (~1–2 s). The `clear()` fix is one line and preserves the same-tick guard because the iOS double-fires within milliseconds, before the coordinator observes `pending`.
- **Location**: `RecipeScalerNative/Routing/DeepLinkRouter.swift:71`, `:81-83`, `:105-111`

#### 2. **[Security]** Silent push handler returns `UIBackgroundFetchResult.failed` for intentional skips → APNs retries forever, drains battery, throttles future silent push

- **Impact**: `WidgetSilentPushHandler.refreshSnapshotFromServer()` returns `false` for `.skippedNoAuth` (signed out) and `.skippedPendingLocal` (optimistic local write in flight). `AppDelegate` maps `false → .failed`. iOS treats `.failed` as "retry with exponential backoff". On a signed-out device or during the 15-s pending-local window, every silent push retriggers itself. Apple also penalizes installs that frequently report `.failed` by reducing future silent-push delivery budget.
- **Recommendation**: Map `.skippedNoAuth` and `.skippedPendingLocal` → `.noData` (intentional no-op). Reserve `.failed` for transient network errors where a retry is useful.
- **Location**: `RecipeScalerNative/RecipeScalerNativeApp.swift:36-39`, `RecipeScalerNative/Services/WidgetSilentPushHandler.swift:96-108`

#### 3. **[Business Logic]** `scheduleLegacyPushMigrationIfNeeded` reads `@MainActor` state from a detached `Task`, races with `sync()` / `stopObservingPushToken` under Swift 6 strict concurrency

- **Impact**: `legacyMigrationTasks[timerId] = Task { [weak self] in … }` is a plain `Task`, not `Task { @MainActor in … }`. The `pushTokenEmissionReceived` / `activityByTimerId` / `createdWithPushTypeToken` reads inside the body are `@MainActor`-isolated vars read from a `@Sendable` closure. Under Swift 6 these are data races. Today they "work" via implicit actor hops, but a migration that should be cancelled can read stale state and `end(timerId:)` an activity that just became healthy.
- **Recommendation**: Mark the task body `@MainActor` so the entire preflight shares the actor. Apply the same to `pushTokenTasks` (line 339) and `activityUpdatesTask` (line 516).
- **Location**: `RecipeScalerNative/Services/TimerLiveActivityCoordinator.swift:391-405` (and `:339-370`, `:514-523`)

#### 4. **[Performance]** Widget Provider timeline completion blocked by up to 8 s of network refresh on slow networks

- **Impact**: `TimerWidgetProvider.getTimeline` calls `await Self.refreshFromNetworkIfPossible()` **before** `completion(...)`. The 8-s `TaskGroup` race between HTTP fetch and a sleep holds the widget extension alive for the full window on lossy networks. Widget shows stale content longer; extension at risk of being killed mid-flight by the OS.
- **Recommendation**: Build the timeline from the cached App Group snapshot first, call `completion(...)` immediately, run the network refresh in a fire-and-forget `Task`, and `WidgetCenter.shared.reloadTimelines(ofKind:)` only if fetched data differs from cache.
- **Location**: `HomeWidgetExtension/TimerWidgetProvider.swift:50-73` (entry), `:85-96` (timeout), `:114-127` (HTTP)

#### 5. **[Architecture]** `WidgetPushRegistrar` register/POST layer has no production caller — dead code masquerading as a wired feature

- **Impact**: `WidgetPushRegistrar.register(tokenHex:)` / `registerCachedIfNeeded()` are constructed in `AppContainer` and unregistered on logout, but `AppDelegate.application(_:didRegisterForRemoteNotificationsWithDeviceToken:)` only routes APNs tokens to `PushRegistrationService`, never to `widgetPushRegistrar`. The entire B2 register layer is scaffolding for an iOS-26+ appex DT bump that hasn't shipped. Readers will assume silent push refresh (B4) is paired with widget token push (B2) — it is not.
- **Recommendation**: Either drop `WidgetPushRegistrar`/`WidgetPushTokenClient.register*` from production until the appex DT bumps (keep tests), or call `widgetPushRegistrar.registerCachedIfNeeded()` from `AppContainer.bootstrap` after APNs registration.
- **Location**: `RecipeScalerNative/Services/WidgetPushRegistrar.swift:14-52`, `RecipeScalerNative/RecipeScalerNativeApp.swift:13-18`, `HomeWidgetExtension/TimerWidgetPushHandler.swift:7-42`

### Medium

#### 6. **[Security]** `WidgetPushTokenClient.unregister` wipes the App Group cache **before** the DELETE — transient failure loses the token client-side forever

- **Impact**: `clearCachedToken()` runs as the first statement of `unregister`. If the DELETE fails (transport, 5xx), the cache is already gone. On next bootstrap, `WidgetPushRegistrar.registerCachedIfNeeded()` finds no cached token and returns early — the server has no widget binding for this device until iOS rotates the token (may never happen). For the next account signing in on the same device, silent `timers` pushes stop refreshing the Lock Screen widget. This inverts the orphan-token class of bug the wipe was supposed to close.
- **Recommendation**: Move `clearCachedToken()` to after a successful DELETE, or into `WidgetPushRegistrar.clearCachedToken()` (the offline-wipe path that already exists). On `.failure`, keep the cache for retry.
- **Location**: `RecipeScalerCore/Networking/WidgetPushTokenClient.swift:81-84`

#### 7. **[Business Logic]** `WidgetPushTokenClient.unregister` reports `.success` for empty `deviceId` even when App Group mirror disagrees with the registered row

- **Impact**: `SharedDeviceId.current()` mints a fresh UUID on App Group wipe / fresh install / unprovisioned simulator. The DELETE then goes out with a `device_id` unrelated to what the server stored at register time; server returns 200 (no row matched); client reports `.success`. Locally the client thinks it's unregistered, but the server row for the real device id survives.
- **Recommendation**: Capture the `deviceId` used at `register` time next to `registeredTokenHex` (e.g. `registeredDeviceIdKey`) and use that for the DELETE. If absent, return `.failure` so the gap is observable.
- **Location**: `RecipeScalerCore/Networking/WidgetPushTokenClient.swift:92-115`, `RecipeScalerCore/Auth/SharedDeviceId.swift:21-34`

#### 8. **[Business Logic]** `WidgetPushTokenClient.register` can issue duplicate POSTs when the same token arrives concurrently from app + widget processes

- **Impact**: No in-flight `Task` gate. Widget extension (`TimerWidgetPushHandler.pushTokenDidChange`) and main app (`WidgetPushRegistrar.registerCachedIfNeeded`) calling near-simultaneously both pass the `registeredTokenHex == tokenHex` dedup, both POST, both write. Server is UPSERT-idempotent, so no data corruption — but redundant network + confusing duplicate `widget_push_token_registered` log entries.
- **Recommendation**: Either accept the duplicate (server idempotent on `(user_id, device_id, token)`) and downgrade to informational, or add a process-local single-flight `actor` matching the `TimerWidgetNetworkRefreshGate` pattern. Cross-process dedup is the server's job.
- **Location**: `RecipeScalerCore/Networking/WidgetPushTokenClient.swift:56-78`

#### 9. **[Architecture]** Three+ duplicated `APIClient.shared` hydration sites from `SharedAuthStore` — drift hazard

- **Impact**: `WidgetSilentPushHandler.refreshSnapshotFromServer`, `WidgetPushRegistrar.configureAPIClientFromSharedAuth`, `TimerWidgetPushHandler.pushTokenDidChange`, and the `AuthService.wipeLocalSession` capture-and-rehydrate path all do the same `if let bearer = SharedAuthStore.token … configure(authToken:)` dance. They live in three different modules and have to stay in sync by hand. A fourth site (`AuthService.wipeLocalSession`) already captures locally before the wipe — the pattern is spreading, not consolidating.
- **Recommendation**: Extract a single `SharedAuthStore.configureSharedAPIClient()` (or `APIClient.configureFromSharedAuth()`) on `RecipeScalerCore`. Every caller invokes one method. Wipe path still needs local capture, but the body becomes one call.
- **Location**: `RecipeScalerNative/Services/WidgetPushRegistrar.swift:77-84`, `RecipeScalerNative/Services/WidgetSilentPushHandler.swift:60-63`, `HomeWidgetExtension/TimerWidgetPushHandler.swift:30-35`, `HomeWidgetExtension/TimerWidgetProvider.swift:114-117`, `RecipeScalerNative/Services/AuthService.swift:461-466`

#### 10. **[Architecture]** `AuthService.wipeLocalSession` reaches back into `AppContainer.shared?` for 5+ services — composition-root rule bending

- **Impact**: `AuthService` is constructed *inside* `AppContainer`, but its wipe path reads `AppContainer.shared?.featureAdoption`, `?.timerLiveActivityCoordinator`, `?.widgetPushRegistrar`, etc. (`AuthService.swift:455, 467, 469, 707, 750, 780`). Commits `4d29d9a` and `656975f` added two more such sites. The order of those calls is significant (capture bearer → wipe keychain → defer LA clear + widget unregister), and any re-ordering has to traverse `AppContainer.shared?` rather than explicit parameters.
- **Recommendation**: Inject a `SessionWipeCoordinator` protocol (or a closure) into `AuthService.init`, owned by `AppContainer`, that runs the full cross-service teardown in the right order. Container knows the order; AuthService shouldn't discover it.
- **Location**: `RecipeScalerNative/Services/AuthService.swift:455, 467-470, 707, 750, 780`

#### 11. **[Architecture]** Two parallel IPC channels for the same Share intent — `openRecipeRequested` notification is dead code

- **Impact**: Spec-025 now writes the imported recipe id to **both** the App Group defaults key (`ShareView.swift:190`) **and** the URL delivery path (`ExtensionHostURLOpener`). The host consumes the App Group key via `consumePendingRecipeIdIfNeeded()`. The `Notification.Name.openRecipeRequested` is declared in `DeepLinkRouter` but **never posted** by any production code — only the verify script `scripts/verify-share-extension.sh:54` still references it, enshrining the dead seam. Future contributors will chase the notification path because it's the most visible, only to find no producer.
- **Recommendation**: Remove `Notification.Name.openRecipeRequested` and the verify rule. The App Group + URL delivery path is the real one.
- **Location**: `RecipeScalerNative/Routing/DeepLinkRouter.swift:232-235`, `RecipeScalerNative/Views/AppShellView.swift:214-216`, `scripts/verify-share-extension.sh:54`

#### 12. **[Architecture]** Live Activity "pending-local" gate has distributed ownership across `TimerLiveActivityIntentPerformer` (set) and `TimerManager.persistTimerSnapshot` (clear)

- **Impact**: Two services mutate the pending-local gate. The 15-s TTL vs clear-on-durable-write logic is implicit and distributed; no shared type owns the contract. The race fix is correct today, but the next person to touch either file has to re-derive the producer/consumer relationship from comments.
- **Recommendation**: Add a thin `TimerSnapshotGate` type (in `RecipeScalerCore`, next to `TimerSnapshotStore`) with `markPending()` / `release()` and an English-named owner. At minimum, a one-line comment in `TimerSnapshotStore.swift` documenting ownership.
- **Location**: `RecipeScalerNative/LiveActivity/TimerLiveActivityIntentPerformer.swift:117-118, 201-202, 275-276`, `RecipeScalerNative/Services/TimerManager.swift:425-428`, `RecipeScalerCore/Snapshots/TimerSnapshotStore.swift:52-75`

#### 13. **[Performance]** `AppContainer.bootstrap` performs a serial network health-check on the critical launch path before sync starts

- **Impact**: On first bootstrap (`!didPerformStaleSessionHealthCheck`), `await auth.performStaleSessionHealthCheck()` runs a `GET /api/settings` round-trip **before** `sync.start(userId:)` / `reminders.attach` / `spotlight.start`. On slow cellular cold-launch this delays first socket connect, Spotlight indexing, and Reminders attach by the full probe latency (200 ms – several seconds). No offline/timeout fast-path for transient errors.
- **Recommendation**: Either run the probe in parallel with `sync.start` and only react (teardown) on `.userMissing` / `.unauthorized`, or give the probe its own short URLSession (5 s). Current sequential pattern is correct but has a real cost on launch.
- **Location**: `RecipeScalerNative/App/AppContainer.swift:276-300` (probe + early returns), `:362-381` (sync.start after)

#### 14. **[Performance]** Live Activity performer / Widget Provider redundantly `TimerSnapshotStore.load()` 2–3× per Intent / timeline refresh

- **Impact**: Each `JSONDecoder` pass over the document is small (≤4 timers) but happens on every Lock Screen tap and every widget timeline reload — multiplied by Intent frequency. `hasPendingLocalMutation(now:)` also reads UserDefaults three separate times inside one call.
- **Recommendation**: Load once into a local at the top of `performNetworkRefresh`. Pass the loaded snapshot into `applyAndSave(load:save:)` via the injected defaults. Read `pendingLocalUntilKey` once.
- **Location**: `HomeWidgetExtension/TimerWidgetProvider.swift:98-149`, `RecipeScalerNative/LiveActivity/TimerLiveActivityIntentPerformer.swift:235-277`

#### 15. **[Security]** `.recipe` size pre-flight uses decompressed-archive limit against compressed file size — ZIP-bomb defense weaker than the comment claims

- **Impact**: `RecipeFileImportCoordinator.stageSecurityScopedFile` rejects when `sourceSize > ThirdPartyImportLimits.maxDecompressedArchiveBytes`. The inline comment claims "a compressed `.recipe` larger than that cannot possibly decode to a valid recipe payload" — false. A small ZIP can decompress to arbitrary size (ZIP bomb). Pre-flight only rejects payloads that are *already* over budget on disk; downstream importer is solely responsible for the decompressed-bytes cap. If the importer's guard has any edge case (e.g. counts only recipe JSON bytes, not images), a malicious AirDrop can fill sandbox disk. The misleading comment hides the weakness.
- **Recommendation**: Either rename the applied limit (`maxCompressedArchiveBytes` — smaller), or tighten the comment to state the pre-flight is a coarse upper bound and the decompressed-bytes guard in the importer is the real ceiling.
- **Location**: `RecipeScalerNative/Services/RecipeFileImportCoordinator.swift:117-122`

#### 16. **[UX / Logic]** `AccountView` "Clear logs" hides both rows after wipe; new log writes do not re-show them without leaving the screen

- **Impact**: `hasDebugLogFile` is initialized in `.onAppear` only. After tapping "Clear logs", the rows disappear synchronously, but `AppLog` writes asynchronously on its `writeQueue` and doesn't push observable updates back. New log writes recreate the file, but the rows stay hidden until the user navigates away and back. For a diagnostics flow where the typical workflow is "reproduce bug → export logs", this forces an extra navigation step every time.
- **Recommendation**: Either keep rows always visible in DEBUG, or have `AppLog.clearLogFiles()` post a `NotificationCenter` event that `AccountView` observes to re-evaluate `currentLogFileURL()`.
- **Location**: `RecipeScalerNative/Views/AccountView.swift:610-640` (clear button), `:42` (`hasDebugLogFile` state)

#### 17. **[Architecture]** `ShareView` hardcodes the App Group key `"routing.pendingRecipeId"` as a string literal

- **Impact**: The consumer reads `DeepLinkRouter.pendingRecipeIdKey` (a `static let` in the **main app target**, not `RecipeScalerCore`). `ShareExtensionUI` can't import `RecipeScalerNative` (correct direction), so the literal is the only option today — but rename the constant on the host side and the extension silently breaks cold-start.
- **Recommendation**: Move `pendingRecipeIdKey` to `RecipeScalerCore` as `public enum RoutingKeys { public static let pendingRecipeId = … }` and import from both sides. Same pattern as `WidgetPushTokenClient.pendingCacheKey` and `SharedDeviceId.appGroupKey`.
- **Location**: `ShareExtensionUI/ShareView.swift:190`, `RecipeScalerNative/Routing/DeepLinkRouter.swift:62`

#### 18. **[Architecture]** `WidgetPushTokenClient` cache setters are `public set` — invites bypass of `WidgetPushRegistrar`

- **Impact**: `pendingTokenHex` / `registeredTokenHex` setters are `public`. App-target code could bypass `WidgetPushRegistrar` and mutate App Group state directly, losing the `AppLog` events and the 401-orphan logging the registrar adds.
- **Recommendation**: Make setters `internal` to `RecipeScalerCore` (forcing writes through `register` / `unregister` / `clearCachedToken`). `TimerWidgetPushHandler` already calls the client through method API, so encapsulation is achievable. If full encapsulation is impractical, add a doc comment: "Use `WidgetPushRegistrar` from the app target."
- **Location**: `RecipeScalerCore/Networking/WidgetPushTokenClient.swift:21-41, 56, 92`
