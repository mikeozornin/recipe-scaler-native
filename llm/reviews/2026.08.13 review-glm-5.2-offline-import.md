# Code Review: master

**Date:** 2026-08-13
**Model:** GLM-5.2 (max) via z.ai proxy
**Scope:** uncommitted changes on `master` — `AppSegmentedControl.swift`, `ImportRecipeSheet.swift`, `specs/010-recipe-import/spec.md`, `Localizable.xcstrings`

## Summary

The change adds per-segment `isDisabled` support to the shared `AppSegmentedControl`, swaps `ImportRecipeSheet`'s native `Picker(.segmented)` for it, and introduces offline handling: Text/Photo segments disable when `!isOnline`, an inline `wifi.slash` banner appears, the sheet auto-falls-back to `.file` on offline transition and on cold-open, and spec 010 US6 is updated. The Standards surface (i18n keys, typography, naming, comments, spec cross-references) is clean — verified against the codebase, not just the diff.

Risk level: **low-to-moderate**. No critical issues. One High finding is a documentation/contract gap on the new public `Segment.isDisabled` field; four Medium findings concern state-coherence edge cases and a11y surface that are worth addressing before this lands or soon after.

**Areas reviewed:** Business Logic, Architecture, Standards.
**Areas skipped:**
- *Security* — change touches no user input parsing, authn/authz, secrets, or queries; the offline state is read from a trusted in-process sync service.
- *Performance* — no DB queries, hot paths, or meaningful allocations added; the `Form` re-renders driven by `isOnline` are bounded and already present pre-change.

## Findings (sorted by priority)

### High

1. **[Architecture]** `AppSegmentedControl.Segment.isDisabled` is undocumented public API with an unenforced selection invariant.
   - **Impact:** The field is part of `Segment`'s public init surface (used by every caller of the control), but has no `///` headerdoc explaining the contract: (a) the control guards taps but does **not** enforce `selection ∈ enabled segments` — a caller can bind a selection whose value is disabled and the UI will render a dimmed, unselectable, but visually-"selected" segment; (b) the only caller (`ImportRecipeSheet`) honors the invariant manually via `onChange(of: isOnline)` + `resetState()`, so future callers will likely re-discover this trap the hard way. This is a classic "leaky abstraction" — the control gained behavioral state without taking responsibility for the invariant that state implies.
   - **Recommendation:** Pick one of:
     - Document the contract on `Segment.isDisabled` and on the type itself: *"Caller is responsible for ensuring `selection` is always an enabled segment. The control does not auto-correct."* Add a `DEBUG`-only `assertionFailure` when `selection` matches a disabled segment at render time.
     - Or, make the control self-healing: in `body`, if `segments.first(where: { $0.value == selection })?.isDisabled == true`, fall back to the first enabled segment internally. This centralizes the invariant and removes the `onChange`/`resetState` ceremony from every caller.

### Medium

2. **[Business Logic]** Auto-fallback to `.file` cascades through `onChange(of: mode)` and silently wipes user-visible errors/progress.
   - **Impact:** `onChange(of: isOnline)` sets `mode = .file`; that triggers `onChange(of: mode)` which sets `errorMessage = nil`, `photoWarning = nil`, `fileImportProgress = nil`. If the user is offline and looking at an error message (e.g. a failed submit's `import.offline-unavailable`), a momentary connectivity flap will wipe it. Same for `fileImportProgress` mid-import. The wiping is undocumented and probably unintentional — the `onChange(of: mode)` handler was written to clear stale errors when the **user** switches tabs, not when the system does.
   - **Recommendation:** Either (a) route the offline fallback through a private setter that skips the wipe, e.g. `private func applyOfflineFallback() { mode = .file /* no error wipe }`, called from `onChange(of: isOnline)`; or (b) document explicitly in `onChange(of: mode)` that system-driven transitions are expected to clear transient state and accept the trade-off.

3. **[Business Logic]** Opening the sheet during the normal `.connecting` launch window strands the user on `.file` with the offline banner on a fully online device.
   - **Impact:** `isOnline` is `connectionState == .connected` — anything else (`.unknown`, `.connecting`, `.disconnected`) is treated as offline. At cold launch the sync service typically spends 1–3s in `.connecting` before reaching `.connected`. If the user opens Import during that window, `resetState()` puts them on `.file`, the offline banner shows, and the asymmetric `onChange(of: isOnline)` (only handles `online == false`) will **not** move them back to `.text` once connection establishes. Result: a confused user on a perfectly online device staring at offline UI. The offline → online transition is silently a no-op.
   - **Recommendation:** Decide the invariant explicitly. Either (a) treat `.connecting` as online for purposes of segment enablement (the user's intent is "I want to import", and the connection will likely establish before they submit), or (b) keep the asymmetric handler but record the pre-offline `mode` and restore it on `online == true` so the user returns to where they were. Option (b) also fixes the next flapping case.

4. **[Architecture]** Offline banner visual is duplicated across at least 5 sites with no shared component.
   - **Impact:** The `Label { Text(...).appBody().foregroundStyle(.secondary) } icon: { AppSymbol.image("wifi.slash").foregroundStyle(.secondary) }` block is now identical in `AccountView`, `TelegramConnectionView`, `AssistantSheet`, and the new `ImportRecipeSheet`. Spec 066 has `OfflineBannerGate` (debounced) but the instant-banner variant has no shared primitive. Drift is already happening (icon size, spacing, typography level will diverge on the next redesign).
   - **Recommendation:** Extract an `OfflineBanner` view (instant variant) and reuse across the 4+ sites. Keep `OfflineBannerGate` as a separate debounced wrapper for the app-wide banner. This is a small refactor that pays off the next time someone touches offline UX.

5. **[Architecture]** Replacing native `Picker(.segmented)` with a custom button-based control silently changes the accessibility contract; the new per-segment disabled state is not exposed via a11y traits.
   - **Impact:** Native `Picker(.segmented)` exposes a single VoiceOver element with `adjustable` trait and increments/decrements through options — a well-understood HIG pattern. The custom `AppSegmentedControl` exposes a container with multiple `Button`s; VoiceOver users now swipe between them instead of adjusting. That may be acceptable (and is consistent with how the control already behaves in recipe detail / shopping sort), but the **new** disabled state is rendered only via `.disabled()` + `.opacity(0.35)` + `.secondary` foreground — VoiceOver will still announce the button but it won't speak "dimmed"/"disabled" unless `.accessibilityAddTraits(.notEnabled)` (or `.accessibilityHidden(true)`) is added. A VoiceOver user tapping a disabled Text segment hears nothing useful.
   - **Recommendation:** Add `.accessibilityAddTraits(segment.isDisabled ? .notEnabled : [])` next to the existing `.isSelected` trait in `segmentButton`. Verify with Simulator accessibility inspection that disabled segments are announced as "dimmed"/"unavailable".

## Recommendation

**Changes Requested** — the change is solid and the Standards surface is exemplary (the Standards reviewer found zero issues after verifying against the codebase). However, finding 1 (public-API contract gap) should be addressed before merge because `AppSegmentedControl` is a shared primitive and the `isDisabled` field will be load-bearing for future callers. Findings 2–3 are state-coherence bugs that will surface as real user-facing confusion (wiped errors during connectivity flaps; online users staring at offline UI after cold launch) and are cheap to fix in the same PR. Findings 4–5 are quality-of-life improvements that can land as follow-ups if needed, though the a11y trait (finding 5) is small enough to include now.
