# Code Review: master (SwiftUI UI Patterns)

**Scope**: Whole iOS app (`RecipeScalerNative`) against `/Users/mike/.agents/skills/swiftui-ui-patterns`, not a commit-range diff. Watch / Share / Action / Widget mentioned only where they share the same patterns.

**Areas reviewed**: Architecture (app wiring, TabView, NavigationStack, sheets, deeplinks), State/Async (ownership, `.task`, loading/error), Components/Performance (List/Form/Scroll/grids/media/previews). Security skipped — UI-pattern review, no auth/input-surface change under review.

**Method**: Per review-isolation, three dedicated `code-reviewer` agents ran in parallel (architecture / state-async / components-performance). This file aggregates their outputs, deduplicated and priority-sorted.

---

## Summary

The shell is in good shape: composition root in `AppContainer`, `.appEnvironment(_:)`, per-tab `NavigationStack` + enum routes, no `@EnvironmentObject`, `@Observable` as the iOS 17 standard. Recipe list, shopping list, process-table cooking, and most Discover collection/profile models already match the skill.

Eleven findings, **none critical**. Six **high**: mutually exclusive shell sheets on three modifiers; in-app URL taps bypass `DeepLinkRouter`; Discover root surfaces cancellation as a server error; public-profile toggle flashes off before load; cached images can paint a stale bitmap after `.task` identity change; assistant transcript does not pin to the latest message; Discover collection/profile grids are fully eager.

Risk: moderate. Highest user-visible bugs are Discover segment-switch error flash, public-profile toggle race, and assistant chat stuck at the top of history.

## Findings (sorted by priority)

### Critical

None.

### High

1. **[Architecture]** Shell presents three independent sheets instead of one enum-driven `sheet(item:)`
   - `RecipeScalerNative/Views/AppShellView.swift` — `shellWithOverlays` (~418–459), `AssistantSheetModifier` (~1046–1071); `AppShellCoordinator.importPresentation`; `ReleaseNotesStore.isSheetPresented`; `showAssistant` / `assistantOpenRequest` / `assistantShakeOpenRequest`
   - Description: The same `tabView` chain attaches `.sheet(item: $coordinator.importPresentation)`, `.sheet(isPresented:)` for release notes, and another `.sheet(isPresented:)` for assistant. Assistant is a boolean plus two side-channel payloads rather than an identifiable presentation value. Clipboard evaluation checks import presentation but not assistant or release notes.
   - Impact: These shell modals are mutually exclusive in UX. SwiftUI does not reliably stack multiple `.sheet` modifiers on one view. Opening assistant (tab or shake) while release notes is up — or setting `importPresentation` while assistant is up — can drop the new sheet, dismiss the current one, or leave payload state out of sync. PI-5 race comments in `assistantObservers` are a symptom of the boolean + side-channel design.
   - Recommendation: One `ShellSheet: Identifiable` (import, release notes, assistant-manual, assistant-open-request, assistant-shake) on `AppShellCoordinator`, presented with a single `.sheet(item:)`. Fold assistant payloads into associated values. Gate clipboard import on that same optional.
   - Skill: `references/sheets.md`; SKILL.md anti-pattern (multiple boolean flags for mutually exclusive sheets)

2. **[Architecture]** In-app URL taps never enter `DeepLinkRouter`
   - `RecipeScalerNative/RecipeScalerNativeApp.swift` — `WindowGroup` (~175–198); `RecipeScalerNative/Views/AccountView.swift` — `Link(destination:)` (~457–461); `RecipeScalerNative/Views/AppShellView.swift` — `openSafari` (~257–260); `RecipeScalerNative/Views/RecipeDescriptionInlineTextView.swift` — `UIApplication.shared.open(link)` (~112–114)
   - Description: External URLs are handled (`.onOpenURL`, Spotlight, browsing-web activity → `DeepLinkRouter.handle`). There is no `OpenURLAction` in the environment. In-app taps use SwiftUI `Link` or `UIApplication.shared.open`. `PublicURLBuilder.publicProfileURL` is a claimed Universal Link that `DeepLinkRouter.parse` already maps to `.openPublicProfile`.
   - Impact: Same-app Universal Links typically open Safari instead of the app. “Your public recipes” leaves the app instead of pushing `DiscoverRoute.profile`. Description / adoption URLs that are in-app destinations never hit the router.
   - Recommendation: Install `.environment(\.openURL, OpenURLAction { … })` at `WindowGroup` that calls `DeepLinkRouter.parse` / `handle` for internal URLs and returns `.systemAction` otherwise. Prefer that over `UIApplication.shared.open` for app-owned hosts. Keep About/Privacy on `InAppSafariView` if they must stay web.
   - Skill: `references/deeplinks.md`

3. **[State/Async]** Discover root treats cancelled loads as failures
   - `RecipeScalerNative/ViewModels/Discover/DiscoverRootModel.swift` — `load()` (21–38); consumed by `DiscoverRootContent` in `DiscoverRootView.swift` (`.task` / `.refreshable`, 157–228)
   - Description: `DiscoverRootModel` is owned by `DiscoverRootView` `@State` and **survives** switching «Подборки» ↔ «Моя лента». `DiscoverRootContent` is destroyed on that switch, which **cancels** `.task { await model.load() }`. `load()` maps cancellation (including `URLError.cancelled`) to `state = .failed(...)`. Sibling models (`DiscoverCollectionModel`, `DiscoverPublicProfileModel`) already use `requestGeneration` + `Task.checkCancellation()` + restore-previous / idle on cancel. `UserFacingAPIError.message` maps `URLError.cancelled` to the “unreachable” copy.
   - Impact: Switching to «Моя лента» while collections are still loading can leave the surviving model in `.failed`. Switching back paints `ContentUnavailableView` until `.task` reloads. Overlapping `.task` + pull-to-refresh can last-write a stale catalog (no generation token).
   - Recommendation: Match collection/profile: bump a request generation, `try Task.checkCancellation()` after fetch, ignore cancellation (keep previous `.loaded` or `.idle`), and only the current generation may publish `.loaded` / `.failed`.
   - Skill: `references/async-state.md`; `docs/agents/ASYNC-LIFECYCLE.md` §1

4. **[State/Async]** Account public-profile toggle never enters loading; defaults to off
   - `RecipeScalerNative/ViewModels/AccountSettingsViewModel.swift` — `isLoading` (line 14), `refresh(syncService:)` (68–132); `RecipeScalerNative/Views/AccountView.swift` — `publicRecipesSection` (393–410)
   - Description: `AccountView` shows `ProgressView` while `viewModel.isLoading`, otherwise the public-profile `Toggle` bound to `publicProfileEnabled`. `isLoading` is initialized `false` and **never assigned**. `refresh()` fetches profile/sharing over the network but does not set a load phase. `publicProfileEnabled` defaults to `false` and is not seeded from `SharingSettingsCache` (unlike `RecipeShareModel`).
   - Impact: First visit (and every cold `@State` VM) shows the toggle as **off** immediately. If the account actually has a public profile, the switch flips on after the fetch. The user can toggle during that window and race `setPublicProfileEnabled` against the in-flight GET.
   - Recommendation: Drive the section from exclusive load state (or at least set `isLoading` around the first fetch with `defer`). Prefer last-known-good cache for the toggle, then refresh. Do not render the toggle until a value is known (cache or network).
   - Skill: `references/async-state.md`; `references/loading-placeholders.md`

5. **[State/Async]** Image views publish decoded bitmaps after `.task` identity change
   - `RecipeScalerNative/Views/RecipeCachedImageView.swift` — `applyImage(from:)` (152–161), `reloadImage()` (120–143); same pattern in `PublicCachedImageView.swift` `applyImage` (115–125) and `AuthAvatarImage.swift` `.task(id: url)` (30–33)
   - Description: Loads correctly use `.task(id:)` (`loadTaskKey` / `url`). After `Task.detached` decode (or `AvatarImageService.image(for:)`, which uses an unstructured in-flight `Task` not cancelled with the view task), the result is assigned to `@State uiImage` with **no** `Task.isCancelled` check and **no** compare against the current URL/`loadTaskKey`.
   - Impact: When `imageUrl` / avatar URL changes on the same view (photo upload, sync, profile avatar replace), a slower previous decode can paint the **old** image on the new identity. List rows with a stable recipe `id` still hit this when only `imageUrl` updates.
   - Recommendation: Capture `loadTaskKey` (or `url`) before await; after decode, assign only if `!Task.isCancelled` and identity still matches. In `AvatarImageService`, cancel or ignore in-flight work for a URL the view no longer wants.
   - Skill: `references/async-state.md`; `docs/agents/ASYNC-LIFECYCLE.md` §1

6. **[Components]** Assistant chat does not stick to latest messages or dismiss the keyboard on scroll
   - `RecipeScalerNative/Views/AssistantSheet.swift` — `messageList` (~237–258), `body` composer (~93–108)
   - Description: The message list is a `ScrollView` + `LazyVStack` with no `ScrollViewReader`, `scrollTo`, `defaultScrollAnchor(.bottom)`, or `scrollPosition`. New/restored/streaming messages append at the bottom while the viewport stays at the top (oldest). The composer is a `VStack` sibling (sticky — good), but the list has no `.scrollDismissesKeyboard(...)`.
   - Impact: Opening a thread with history, sending a prompt, or watching a stream leaves the latest bubble off-screen. Dragging the transcript also does not interactively dismiss the keyboard.
   - Recommendation: Pin the transcript with `.defaultScrollAnchor(.bottom)` (iOS 17+) or `ScrollViewReader` + a bottom sentinel. Add `.scrollDismissesKeyboard(.interactively)` on the message `ScrollView`. Prefer `.safeAreaInset(edge: .bottom)` for the composer so keyboard avoidance matches the input-toolbar pattern.
   - Skill: `references/input-toolbar.md`, `references/scrollview.md`

7. **[Performance]** Discover collection/profile recipe grids are fully eager
   - `RecipeScalerNative/Views/Discover/DiscoverRecipeCard.swift` — `DiscoverRecipeCardGrid` (~111–157); used from `DiscoverCollectionView.content` (~95) and `DiscoverPublicProfileView.content` (~119)
   - Description: The grid is an eager `VStack` of `HStack` rows, keyed by `ForEach(rows.indices, id: \.self)`, with a comment that this avoids `LazyVGrid` image unload. `DiscoverImageMemoryCache` already exists for that unload problem. Row identity is the row index, so rotation, width preference updates, and search filtering reshuffle the outer `ForEach`. First layout starts at `availableWidth == 0` (1 column) then reflows.
   - Impact: A large collection or public profile keeps every 16:9 card (and decoded image view) alive while scrolling.
   - Recommendation: Use `ScrollView` + `LazyVGrid` with `.adaptive(minimum: 280)` (or the existing column math) and stable `Item.id`. Rely on `DiscoverImageMemoryCache` / disk cache for reappear instead of keeping the whole grid mounted.
   - Skill: `references/grids.md`, `references/scrollview.md`, `references/performance.md`

### Medium

8. **[Architecture]** Profile tab root still uses `@Environment(Observable.self)` after sibling tabs were converted to init injection
   - `RecipeScalerNative/Views/AccountView.swift` — tab root (~16–24, 112+); contrast `RecipeListView`, `ShoppingListView`, `DiscoverRootView`, `YDocRecipeDetailView`
   - Description: Discover / Recipes / Shopping tab roots (and pushed recipe detail) take `YjsSyncService`, `AppShellCoordinator`, `TimerManager`, etc. as stored properties because iOS 26 remasures `NavigationStack` chrome after assistant dismiss in a fallback environment and `@Environment(SomeObservable.self)` traps. `AccountView` still reads seven `@Environment(Observable.self)` values. Auth/timer were already moved to init (comment “architecture review C2”); the rest were not.
   - Impact: After assistant dismiss, visiting or remasuring Profile can trap in `EnvironmentValues.subscript.getter` — the failure mode already documented and fixed on the other tabs. Wiring is inconsistent at the shell.
   - Recommendation: Same contract as `RecipeListView`: pass app-level observables into `AccountView` from `AppShellView`. Keep `@Environment` for non-Observable values (`locale`, `dismiss` on nested sheets only).
   - Skill: `references/app-wiring.md`

9. **[Performance]** `AnyView` type-erases sheets and composer chrome
   - `RecipeScalerNative/Utils/AppSheetChrome.swift` — `OpaqueSheetPresentationModifier` (~82–90); `RecipeScalerNative/Views/AssistantComposer.swift` — `AssistantComposerChrome.topContent` (~31, 52)
   - Description: Sheet chrome wraps the entire presented tree in `AnyView` to optionally apply `presentationDetents`. Composer chrome stores `@ViewBuilder var topContent: () -> AnyView` instead of a generic `TopContent: View` slot.
   - Impact: Assistant, import, collections, and other sheets lose concrete identity for the whole modal content.
   - Recommendation: Make `AssistantComposerChrome<TopContent: View>` generic. For sheet detents, branch with `@ViewBuilder` / `Group` (or two modifiers) instead of `AnyView`.
   - Skill: SKILL.md anti-patterns; `references/performance.md`

10. **[Components]** High-traffic Discover/detail first-load is a spinner, not a skeleton
    - `DiscoverRootView` (~38–40, 158–160); `DiscoverFeedView.content` (~56–72); `DiscoverCollectionView` (~26–27); `DiscoverPublicProfileView` (~33–34); `DiscoverRecipeView` (~97–111); `YDocRecipeDetailView.body` (~292–295)
    - Description: These screens swap to a centered `ProgressView` (or empty title + spinner) until data arrives. There is no `.redacted(reason: .placeholder)` skeleton that preserves card/row/hero layout. Empty/error paths correctly use `ContentUnavailableView` after load.
    - Impact: Network-bound Discover (and a cold recipe-detail open) shows a blank/spinner frame, then a layout jump into the real hierarchy.
    - Recommendation: Render a small fixed set of placeholder cards/rows/hero+title using the real layout, redacted, then swap to loaded/empty. Keep `ContentUnavailableView` for failed/empty after load.
    - Skill: `references/loading-placeholders.md`

11. **[Components]** Primary interactive screens have no `#Preview`
    - `ShoppingListView.swift`, `YDocRecipeDetailView.swift`, `AssistantSheet.swift` / `AssistantComposer.swift`, `DiscoverRootView.swift`, `DiscoverFeedView.swift`, `DiscoverRecipeView.swift`, `DiscoverCollectionView.swift`, `DiscoverPublicProfileView.swift`
    - Description: No `#Preview` on these high-traffic screens. Recipe list, account, and process-table cooking do have previews. Existing list/account previews also hit `TimerManager.shared` rather than an isolated fixture.
    - Impact: Empty, loading, offline, and long-content states for shopping, detail, assistant, and Discover cannot be inspected without a full app bootstrap (Yjs/network).
    - Recommendation: Add `#Preview` for loaded + empty/offline (and assistant empty thread) using `YjsSyncService.makeForTesting` / in-memory stores already used by `RecipeListView` and `ProcessTableCookingView`. Avoid live network and global singletons in preview setup.
    - Skill: `references/previews.md`

### Low

None retained. Nitpicks (missing preview on tiny helper views, debug-only screens) were dropped.

## What looks aligned

- Composition root: services built in `AppContainer.init`, installed with `.appEnvironment(_:)`. `AppContainer.shared` documented for AppIntents / AppDelegate / pre-bootstrap. No `@EnvironmentObject`.
- `AppShellCoordinator` lives on the container so theme/locale `ContentView` churn does not wipe per-tab `NavigationPath`s.
- TabView + independent stacks: Discover / Recipes / Shopping bind coordinator paths; enum `navigationDestination(for:)`. Assistant is a fake tab intercepted in bindings (`tabview.md`).
- Import, recipe-list, and account legal/seed sheets already use `.sheet(item:)` + enums. `ImportRecipeSheet` calls `dismiss()` internally.
- iOS 17+ standard is `@Observable` + `@State` at the owner. `ObservableMigrationTests` matches (`RecipeListViewModel` removed).
- Discover collection/profile models: `LoadState`, `loadIfNeeded`, request generation, cancellation restore.
- Search: local `@State` query + cancellable debounce stores, not body-driven networking.
- Recipe list: `List` + `.searchable`, stable `ForEach` IDs, `EquatableView` rows, `AppEmptyState`.
- Recipe detail: `DetailScrollViewProbe` finds the host scroll instead of a parallel gesture machine; inner ingredient `List` is `.scrollDisabled(true)`.
- App shell: transient toast via `.overlay`; iOS 26.2 timer panel uses `safeAreaBar`.
- `HeroPhotoZoomContext: ObservableObject` is a justified exception (keep pinch ticks off `AppShell` `@State`).

## Recommendation

**Changes Requested.** No critical issues, but six high-priority pattern violations will produce real user-facing races (Discover error flash, public-profile toggle, stale images, stacked sheets, Safari instead of in-app profile, assistant stuck at oldest message).

Suggested fix order if implementing:

1. Discover cancel-as-failure + public-profile loading (user-visible correctness, small diffs)
2. Image stale-assign after `.task(id:)`
3. Single `ShellSheet` enum + `AccountView` init injection (iOS 26 trap)
4. In-app `OpenURLAction` → `DeepLinkRouter`
5. Assistant scroll-to-bottom + keyboard dismiss
6. Lazy Discover grids
7. Medium: skeletons, drop `AnyView`, previews
