## 1. Каждая локальная правка кодирует, сохраняет и отправляет документ целиком

### Причина

`DocumentManager.persistAndDeliver` (`RecipeScalerNative/Services/YjsSync/DocumentManager.swift:707-733`):

```swift
_ = await doc.consumePendingLocalUpdates()          // инкрементальный delta выбрасывается
guard let state = await doc.encodeStateAsUpdate()   // полный документ
...
try await store.saveLocalSnapshot(docKey: docKey, state: state)
Task { await handler(capturedContext, state) }      // в сеть уходит полный документ
```

Путь вызывается на каждый `mutateRecipe`, `mutateRecipeMetadata`, `updateCollectionEntry` (пин, переименование, цвет, порции, ингредиенты).

Дальше то же состояние кодируется и пишется ещё дважды:

- `YjsSyncService.sendDebouncedUpdate` → `documentManager.persistSnapshot` (`YjsSyncService.swift:2674`) — второй полный encode + запись в SQLite;
- `sync_confirmed` → `encodeStateAsUpdate()` + `store.saveSnapshot` (`YjsSyncService.swift:2836-2841`) — третий.

### Доводы

- Стоимость правки — O(размер документа), а не O(изменения). Recipe-документы создаются с `Y_SKIP_GC` (`Services/Yrs/YrsDocument.swift:91`), история не собирается, документ только растёт. Коллекция по комментариям в коде ~400 КБ (`YDocStore.swift:217`, `YjsSyncService.swift:2754`).
- Payload > 32 КБ идёт через сериализованную очередь emit со сном 400 мс до и 900 мс после (`YjsSyncService.swift:2768-2797`) — пин рецепта в большой коллекции блокирует очередь на ~1.3 с.
- Офлайн каждая правка кладёт в `offline_sync_queue` ещё одну полную копию; при reconnect / cold start `applyOfflineQueueToLocalDocs` переигрывает их все (O(строки × размер)).
- Полные состояния попадают в `UpdateDebouncer.flush` → `YjsMergeHelper.mergeUpdates` (см. п. 2) — самый дорогой путь получает самые большие входы.
- Комментарий `DocumentManager.swift:1526` прямо говорит: «yrs re-encode breaks web XmlFragment parsing», а контракт `specs/002-native-editing/contracts/sync-write-protocol.md` — «никогда yrs `encodeStateAsUpdate` на сервер» для описания. Полный yrs-state при правке названия/ингредиента включает перекодированный yrs фрагмент описания; delta содержит только затронутые структуры, т.е. переход на delta этот риск **снижает**.

### Предложение

1. В `persistAndDeliver` отправлять delta:
   ```swift
   guard let delta = await doc.consumePendingLocalUpdates(), delta.count > 2 else { return }
   scheduleSnapshotPersist(docKey: docKey)            // отложенный persist вместо немедленного
   Task { await handler(capturedContext, delta) }
   ```
   Склейка нескольких транзакций уже делается нативно в `UpdateObserverBox.consumePending` (`YrsDocument.swift:33-41`).
2. Персист — через существующий `scheduleSnapshotPersist(docKey:)` (уже используется описанием, `DocumentManager.swift:1522`). Защита от убийства процесса уже есть: `flushAllScheduledSnapshotPersists` на `.inactive`.
3. Убрать `persistSnapshot` из `sendDebouncedUpdate` (`YjsSyncService.swift:2674`) — заменить на отложенный; в `sync_confirmed` обновлять только `lastSyncedAt`, без перекодирования.
4. Путь восстановления не меняется: при неудачном emit — offline queue; флаг unsynced снимается только по `sync_confirmed`; при reconnect по-прежнему уходит полный wire state (`refreshWireSnapshotsForRecipes` / `pushUnsyncedWireSnapshots`). Полное состояние остаётся только на пути восстановления.

### Риски

- **Сервер.** До начала проверить в `recipe-scaler-web`, что `sync_request.yjsUpdate` применяется через `Y.applyUpdate` (а не заменяет документ / не трактуется как full state). Если трактуется как full state — изменение ломает данные.
- **Потерянный delta.** Если сервер принял delta N, но не получил N-1, у него останутся pending-структуры. Покрывается reconnect-путём (полный wire state для unsynced) и sync step 1/2; стоит явно проверить сценарий «обрыв посреди серии правок».
- Офлайн-очередь начнёт хранить много маленьких delta вместо нескольких больших копий — drain склеивает их (см. п. 2).

### Проверка

- Двусторонняя матрица из `sync-write-protocol.md`: iOS edit → web < 5 с; web edit → iOS.
- Офлайн: серия правок (название, порции, ингредиент, описание) → online → web видит всё.
- Логи: размер `sync_request` на правку — байты/единицы КБ, а не сотни КБ.

## 2. `YjsMergeHelper` маршалит байты по одному на главном потоке

### Причина

`YjsMergeHelper` — `@MainActor` (`Services/YjsSync/YjsMergeHelper.swift:10`):

```swift
let arrays = parts.map { $0.map { NSNumber(value: $0) } }        // объект на каждый байт
let script = "window.__yjsMerge.mergeUpdates(\(Self.jsonArray(arrays)))"  // JSON в строку
...
guard let numbers = value as? [NSNumber] ...                       // обратно [NSNumber]
return Data(numbers.map { UInt8(truncating: $0) })
```

JS-сторона (`Resources/DescriptionEditor/yjs-merge-helper.html`) возвращает `Array.from(Uint8Array)` — т.е. ответ тоже массив чисел.

Вызывается из:

- `UpdateDebouncer.flush`, когда за 1 с накопилось ≥ 2 апдейта (`UpdateDebouncer.swift:116`);
- `flushPendingUpdates` (`YjsSyncService.swift:508`);
- drain офлайн-очереди `resolveYjsPushPayload` (`YjsSyncService.swift:3047-3066`);
- `refreshWireSnapshotForRecipe` (`YjsSyncService.swift:2626`), который планируется на каждое офлайн-обновление описания.

### Доводы

- Документ 400 КБ → ~400 тыс. `NSNumber` + многомегабайтная JSON-строка, собранная и разобранная на главном потоке, в обе стороны. Это фриз в десятки–сотни мс на вызов.
- Из-за п. 1 входы — полные документы, поэтому худший случай — обычный: две быстрые правки подряд.
- JS-хелпер выбран сознательно (web parity для wire-байтов описания), поэтому его надо ускорить, а не убрать.

### Предложение

**A. Сразу, низкий риск — base64 вместо массивов чисел.**

Swift:
```swift
let payload = parts.map { $0.base64EncodedString() }     // JSON-массив строк
let script = "window.__yjsMerge.mergeUpdates(\(jsonStringArray(payload)))"
let value = try await webView.evaluateJavaScript(script)
guard let b64 = value as? String, let data = Data(base64Encoded: b64) else { throw ... }
```

JS:
```js
function fromB64(s) { var bin = atob(s); var u = new Uint8Array(bin.length);
  for (var i = 0; i < bin.length; i++) u[i] = bin.charCodeAt(i); return u; }
function toB64(u) { var s = ''; for (var i = 0; i < u.length; i += 0x8000)
  s += String.fromCharCode.apply(null, u.subarray(i, i + 0x8000)); return btoa(s); }
```

Боксинг и JSON уходят с главного потока; декодирование — в процесс WebContent; `evaluateJavaScript` передаёт одну строку. Тот же приём стоит применить к мосту редактора (`Views/DescriptionEditorWebView.swift:183-197`, `Views/DescriptionEditorBridge.swift:226-233`).

**B. Не вызывать merge, когда он не нужен.**

- Пока п. 1 не сделан: в батче дебаунсера лежат полные состояния одного документа — новейшее включает все предыдущие, достаточно отправить последнее.
- После п. 1: в батче маленькие delta, merge дешёвый. Апдейты из yrs можно склеивать нативно существующим `mergeYjsUpdates` (`YrsDocument.swift:44`), для этого разделить в дебаунсере источник «yrs» / «wire из WebView». Wire-байты описания оставить в JS (контракт).
- Внимание: `mergeYjsUpdates` создаёт временный документ через `ydoc_new()` без `Y_SKIP_GC`. При расширении использования — создавать его с тем же флагом, что `YrsDocument.swift:91` (обоснование — `docs/DECISIONS.md`, решение про Tiptap / yjs 13).

### Риски

- A — формат меняется только между Swift и бандлом в одном приложении; риск — ошибка кодирования, закрывается тестом.
- B — «отправить последний полный state» корректно только пока в батче нет wire-delta описания; поэтому B делать вместе с разделением источников.

### Проверка

- Юнит-тест: новые `mergeUpdates` / `encodeFullState` дают байт-в-байт тот же результат, что старая реализация, на фикстурах (пустой, маленький, ~400 КБ документ).
- Ручной сценарий: офлайн-правки описания → reconnect → web видит описание без поломки XmlFragment.

## 3. Регулярные выражения по имени рецепта — тысячи раз на главном потоке

### Причина

`RecipeTitleEmoji.displayName` / `leadingEmoji` (`Utils/RecipeTitleEmoji.swift:36-72`) — 1–3 `NSRegularExpression` на вызов. `compareNames` вызывает `displayName` для обеих сторон на **каждое сравнение**. Горячие места:

- `CollectionRecipesIndexBuilder.sortForDisplay` (`Utils/CollectionRecipesIndex.swift:87-97`) — `live`, `uncategorized` и каждая папка; вызывается из `refreshCollectionEntries` на `@MainActor` после каждой синхронизации, даже если записи не изменились (`YjsSyncService.swift:3882`).
- `RecipeListView.swift:284-289` — на **каждое нажатие** в поиске пересортировка всей библиотеки:
  ```swift
  let sorted = RecipeTitleEmoji.sortCollectionEntries(syncService.collectionEntries)
  searchStore.refresh(entries: sorted, query: query)
  ```
- `RecipeRowData.init` (`RecipeListView.swift:877-885`) — 2 регулярки на строку; `pinnedRowItems` / `unpinnedRowItems` — computed properties, читаются 2–4 раза за `body` (`RecipeListView.swift:89-108`); то же в `CollectionFolderView.swift:441-454` и `pinStateSignature` (`:109`).

### Доводы

- 500 рецептов: сортировка ≈ 4 500 сравнений × 2–4 регулярки ≈ 10–20 тыс. прогонов на проход; row data — ещё ~3 000 на `body`.
- `body` списка перевычисляется при каждой дельте синхронизации, смене `connectionState`, свайп-шитах, изменении панели таймеров.
- Пересортировка в поиске бессмысленна: `sortCollectionEntries` и `sortForDisplay` — один и тот же компаратор (пины первыми → имя → id), т.е. результат идентичен уже готовому `collectionIndex.live`.

### Предложение

1. `CollectionEntry` (`Models/YDoc/CollectionEntry.swift`): добавить `let displayName: String` и `let leadingEmoji: String?`, вычислять в `init`. Записи строятся в акторе `DocumentManager` — вне главного потока; вызывающий код не меняется; синтезированный `Equatable` остаётся корректным (поля производные).
2. `RecipeTitleEmoji`: компаратор на готовых полях (`displayName` → при равенстве `localizedStandardCompare` по исходному имени → id). Использовать в `sortForDisplay` и `sortCollectionEntries`. Регулярок: с ~4·n·log n до n на обновление.
3. `RecipeRowData.init` — брать `entry.displayName` / `entry.leadingEmoji`. Массивы строк считать один раз за `body` (`let`) или хранить в индексе.
4. `RecipeListView.swift:287` → `searchStore.refresh(entries: syncService.collectionIndex.live, query: query)`.
5. Опционально: в `refreshCollectionEntries` не пересобирать индекс, если `collectionEntries == filtered`; сборку — вне главного потока.

### Риски

Низкие: чистая мемоизация. Единственное — не разойтись с web `compareRecipeNamesIgnoringLeadingEmoji` (логика сравнения не меняется, меняется только место вычисления).

### Проверка

- Существующие тесты сортировки — порядок не меняется.
- Новый тест: эмодзи-префиксы, ZWJ-последовательности, совпадающие display-имена с разными исходными.

## 4. Таймеры: работа Live Activity каждые 3–5 с и бесконечный 1 Гц цикл

### Причина

**a. Миниатюра.** `TimerLiveActivityMetadataProvider` — `@MainActor` (`Services/TimerLiveActivityMetadataProvider.swift:15`). На каждый `sync` (`:33-58`): `UIImage(contentsOfFile:)` (с фолбэком на `.full`), отрисовка в 24×24, `jpegData`, атомарная запись в App Group. Кэша нет.

**b. Лишние `Activity.update`.** `updateRunningTimers` (`Services/TimerManager.swift:568-581`) на каждом тике вызывает `syncLiveActivityProgress` (раз в 3 с на таймер, `:606-620`) или `syncLiveActivityIfOverdue` (раз в 5 с, `:625-636`). `makeContentState` всегда ставит `syncedAt: Date()` (`TimerLiveActivityCoordinator.swift:581`), поэтому каждое обновление — «изменение».

**c. Цикл не останавливается.** `handleTimerReachedZero` (`TimerManager.swift:638-645`) ставит `hasCompleted = true`, но `isRunning` остаётся `true`; `stopUpdateLoopIfIdle` (`:461-465`) проверяет только `isRunning` → 1 Гц `Timer` работает, пока пользователь не удалит завершённый таймер.

### Доводы

- (a) + (b): декодирование, ресайз, JPEG-кодирование и запись на диск на главном потоке каждые 3–5 с на каждый таймер — хитчи при скролле в режиме готовки (именно там таймеры и запущены). Плюс `reconcile` на каждое изменение `collectionEntries` (`ContentView.swift:250-256`) повторяет то же.
- Периодические обновления разрешены только при `applicationState == .active` (`TimerManager.swift:605-615`), т.е. когда Lock Screen и Dynamic Island этого приложения **не видны**. Сам отсчёт виджет рисует без обновлений: `Text(timerInterval:)` и `ProgressView(timerInterval:)` (`TimerLiveActivityExtension/TimerLockScreenLiveActivityView.swift:153,163,256`, `TimerLiveActivityWidget.swift:45`), фаза exceeded считает вверх через `countsDown: false`.
- Что действительно зависит от времени на момент рендера: цвет акцента (`TimerLiveActivityAccent.resolve(remainingSeconds:totalDuration:)`, `TimerLockScreenLiveActivityView.swift:36`) и AOD-текст «44m» (`:141`). Это дискретные переходы, а не непрерывная величина — их достаточно отправлять при смене.
- (c): забытый завершённый таймер = пробуждение главного потока раз в секунду + update Live Activity раз в 5 с всё время, пока приложение открыто. Тик нужен только для обнаружения момента окончания — панель тикает сама через `TimelineView` (комментарий `TimerManager.swift:556-559`).

### Предложение

**a. Миниатюра.**
- Если `la-thumb-<recipeId>.jpg` существует и не старше исходного `.preview` — сразу вернуть имя (плюс in-memory `[recipeId: fileName]`).
- Генерация вне главного потока (`nonisolated` + `Task.detached`), через ImageIO `CGImageSourceCreateThumbnailAtIndex`; только `.preview`, без фолбэка на `.full`.
- Попутно: 24×24 px размыто на 3x-экранах — `maxPixelSize: 72`.

**b. Обновлять только при смене визуального состояния.**
- В `TimerManager`: вместо периодических `syncLiveActivityProgress` / `syncLiveActivityIfOverdue` хранить `lastSentBucket[timerId]`, где bucket = `phase` + `TimerLiveActivityAccent.resolve(...)`; синк — только при смене bucket.
- В `TimerLiveActivityCoordinator.sync`: хранить последний отправленный `ContentState`, пропускать `activity.update`, если он совпадает без учёта `syncedAt`; `syncedAt` ставить только при реальной отправке.
- Гарантировать один финальный синк всех таймеров при переходе сцены в `.inactive` / `.background` (свежий AOD-текст на Lock Screen; дальше — APNs, spec 058).

**c. Остановка цикла.**
- `stopUpdateLoopIfIdle`: `!timers.contains { $0.isRunning && !$0.hasCompleted }`; вызывать в конце `handleTimerReachedZero`.
- Лучше: заменить повторяющийся `Timer` одноразовым до ближайшего `endTime`.

### Риски

- Spec 058: локальные обновления не должны перетирать APNs-состояние паузы — предложение уменьшает число локальных обновлений, т.е. риск снижается. Сохранить существующие guard'ы (`shouldSkipBackgroundRunningUpdate`, `suppressProgressLiveActivitySync`).
- Если какой-то элемент виджета всё же зависит от свежего `syncedAt` (комментарий: «Bumped on each coordinator sync so Lock Screen re-renders after extension UI changes») — проверить вручную после обновления расширения.

### Проверка

- 2 таймера; один завершается; заблокировать телефон → Live Activity в фазе exceeded, считает вверх; цвет меняется в последние 10%.
- AOD: компактный текст актуален после блокировки.
- `AppLog`: `Activity.update` — только при смене фазы/bucket; после завершения всех таймеров 1 Гц цикл остановлен.
- Time Profiler: нет `UIImage(contentsOfFile:)` / `jpegData` на главном потоке во время готовки.

## Приложение: остальные находки (кратко)

### Синхронизация и хранилище
- Одно изменение запускает 2–3 полных refresh (deep observer + прямой вызов): коллекция `YjsSyncService.swift:3577`, рецепт `:3559`, список покупок ×3. `currentRecipe` / `shoppingSnapshot` присваиваются без `!=`; `RecipeData` не `Equatable` (`Models/YDoc/RecipeData.swift:5`).
- Foreground / reconnect грузит из SQLite снапшоты **всех** рецептов до фильтра unsynced (`YjsSyncService.swift:652, 2559-2574`).
- `DocumentManager.docs` никогда не вытесняется (Spotlight и поиск загружают все документы); `persistAll` перекодирует все документы на каждом `.background` без `beginBackgroundTask` (`DocumentManager.swift:437-446`).
- Каждый входящий апдейт с сервера → полный encode + запись (`DocumentManager.swift:192-194`).
- HTML-кэш описания сбрасывается любой правкой рецепта (`DocumentManager.swift:722-723`), ключ — state vector всего документа.
- Socket.IO без `.handleQueue(...)` — обработчики, вероятно, на main (`YjsSyncService.swift:1756-1765`).
- Офлайн-очередь переигрывается на cold start до `isLocalDataLoaded`, на reconnect и при открытии рецепта (`DocumentManager.swift:665-687`).
- Офлайн-правка описания — недебаунсенный полный persist на каждый апдейт WebView (`YjsSyncService.swift:2489-2497`).
- Префетч картинок: уведомление на каждую картинку всем `RecipeCachedImageView`, пересчёт cache status каждые 300 мс; метаданные — 6 ключей на рецепт в UserDefaults.
- Мелочи: `DatabaseQueue` вместо `DatabasePool`; `ISO8601DateFormatter()` на каждую запись; нет индекса по `recipeId` в `offline_sync_queue`.

### Списки, поиск, Discover
- Поиск: `normalizeForSearch` (аллокация String на символ) по всем загруженным ингредиентам и описаниям + построение подсветки — на каждое нажатие на main (`ViewModels/RecipeListSearchStore.swift:148-194`, `Utils/RecipeSearchUtils.swift:218-237, 317-400`).
- Discover: неленивая сетка (`Views/Discover/DiscoverRecipeCard.swift:111`, намеренно), каждая карточка декодирует 800 px; подсветка пересобирается на каждое нажатие.
- `CollectionFolderView`: `.id(pinStateSignature)` (`:159`) пересоздаёт List во время поиска; линейный `collectionEntries.first{}` на строку (`:478-480`).
- Строки списка префетчат 800 px в общий кэш с 132 px превью (лимит 80 / 48 МБ) → мерцание миниатюр при быстром скролле (`RecipeListView.swift:571-579`, `CollectionFolderView.swift:533-541`).
- Список покупок: матчер иллюстраций на каждую строку на каждый рендер, включая каждое нажатие в поле добавления (`ShoppingListView.swift:325, 392`).
- `DiscoverAvatar`: `Data(contentsOf:)` + полный декод на main (`DiscoverRootView.swift:477-509`); Discover-экраны перезагружаются при каждом появлении.

### Детали рецепта и готовка
- `RecipeDescriptionParser`: регулярка компилируется на каждый вызов, копирование остатка HTML на каждый блок, на main, `UUID()` на блок → полный пересбор ForEach. **Вероятный краш:** `RecipeDescriptionParser.swift:120-121, 223` смешивает UTF-16 смещения `NSRange` с Character-индексами — эмодзи в описании может вывести индекс за границу (не проверено в рантайме).
- `AppNumberFormat` создаёт `NumberFormatter` на каждое число (`Utils/AppNumberFormat.swift:25`) — ~7 на строку ингредиента при каждом нажатии на порции.
- Детали рецепта зависят от всего `collectionEntries` (`YDocRecipeDetailView.swift:157, 268`).
- Режим готовки: JSON-декод таблицы + HTML-регулярки + SHA-256 на каждый `body` (`Views/Cooking/ProcessTableCookingView.swift:23-30, 144-164`).
- Ингредиенты: `List` внутри `ScrollView` с высотой из измерений через PreferenceKey — минимум два прохода layout (`YDocIngredientsSection.swift:83-132`).

### Ассистент, импорт, запуск
- Стриминг: каждый чанк перерисовывает весь sheet — lookups по коллекции, `DateFormatter` в каждой строке, полный перепарсинг markdown; частичные ответы вытесняют `MarkdownCache` (лимит 64) (`Views/AssistantSheet.swift:241, 951-954`, `Utils/MarkdownCache.swift:41-58`).
- Cold start: ~14 синхронных вызовов keychain на main, включая delete+add неизменённых credentials в двух группах (`Services/AuthService.swift:634-650`).
- Reminders: квадратичная работа с EventKit и самоперезапуск через `EKEventStoreChanged` (`Services/Reminders/RemindersSyncService.swift`).
- Импорт фото: оригиналы до 25 МБ, все параллельно, хотя есть даунскейлер до 2560 px (`Utils/ImportPhotoLibrary.swift:224-237, 317-328`).
- Мелочи: каждый foreground удаляет и вставляет все таймеры в SwiftData; панель таймеров тикает при всех на паузе; индикатор голоса перерисовывает весь composer; экран аккаунта — три последовательных сетевых вызова.
