# Code Review: master (весь проект) — 2026.09.04

- **Модель:** GLM-5.3-Flash (code-review skill, 5 параллельных ревьюеров)
- **Объём:** ~60k строк Swift: RecipeScalerNative (298 файлов), RecipeScalerCore, расширения (Share/Action/HomeWidget/TimerLiveActivity/Watch), 162 тестовых файла
- **Области:** Security, Business Logic/Correctness, Performance, Architecture, Standards
- **Итог:** 39 находок — 1 critical, 7 high, 14 medium, 17 low. Критических проблем безопасности нет; главные риски — надёжность sync/таймеров и main-thread декод изображений.

## Summary

Проект в хорошей форме для своего размера: composition root соблюдается, расширения чистые и ходят в Core-фасады, i18n-lint зелёный, миграции GRDB корректны, внешние файлы импортируются с тройными лимитами, deep links с allowlist хостов и UUID-валидацией, креды в Keychain с device-only accessibility. Слабые места сосредоточены в трёх кластерах: (1) надёжность sync-конвейера и таймеров — один сбой WebContent-процесса может навсегда зависить offline-очередь, logout не чистит таймерное состояние между аккаунтами, офлайн-созданные таймеры теряются при pull; (2) производительность UI — синхронный декод 800px-картинок на main thread при скролле Discover и посекундная перезагрузка widget timeline; (3) раскрученные god-объекты (`YjsSyncService` 4693 строки) и обход DI через `.shared`.

## Findings

### Critical

1. **[Performance]** Декодирование Discover-картинок на MainActor при скролле
   - `DiscoverImageLoader.loadImage` декодирует файл синхронно на акторе вью: `RecipeScalerNative/Views/Discover/DiscoverRecipePreviewImage.swift:36-43` (disk-hit → `RecipeImageDecoder.decode` без `await`) и `:44-53`; вызывается из `.task(id: url)` → MainActor. Размер декода — 800px. Аватары: `RecipeScalerNative/Views/DiscoverRootView.swift:439` → `loadAvatar` `:474-501` → `decodeFullImage` `:503-506` — `Data(contentsOf:)` + полный `UIImage(data:)` на main.
   - Impact: каждая ячейка с disk-hit и memory-miss делает CGImageSource-декод 5–30мс на main-треде → пропущенные кадры при скролле; на холодном старте кэша — джанк на весь первый проход ленты.
   - Recommendation: декод в `Task.detached(priority: .userInitiated)` (паттерн уже есть в `RecipeCachedImageView.applyImage`, `RecipeCachedImageView.swift:152-161`); для аватаров — downsampled-декод вместо полного `UIImage(data:)`.

### High

2. **[Business Logic]** Permanent hang sync-конвейера после неудачной загрузки WKWebView в `YjsMergeHelper`
   - `RecipeScalerNative/Services/YjsSync/YjsMergeHelper.swift:49-68` (`ensureReady`) + `:117-123` (`didFail`): при неудачной навигации waiters ресумятся, но `webView` не обнуляется и `ready` остаётся `false` — все последующие `ensureReady()` навсегда подвисают на `withCheckedContinuation` (`:64`) без таймаута и cancellation handler. Критический путь: `YjsSyncService.swift:3133` (`resolveYjsPushPayload`), `UpdateDebouncer.swift:116` (`flush`).
   - Impact: один сбой загрузки `yjs-merge-helper.html` (memory pressure убил WebContent-процесс) — `drainOfflineQueue` зависает до конца жизни процесса; `pendingReconnectSyncTask?.cancel()` не может прервать зависшую задачу.
   - Recommendation: в `didFail` обнулять `webView` (разрешить retry) и резюмить waiters с ошибкой; таймаут вокруг `evaluateJavaScript`/`ensureReady`; `withTaskCancellationHandler`.

3. **[Business Logic]** Logout / смена аккаунта не чистит таймеры: события перетекают в следующий аккаунт
   - `RecipeScalerNative/App/AppContainer.swift:542-562` (`stopForLogout`) не трогает `TimerSyncService` и `TimerManager`. Состояние `TimerSyncService` персистится в `UserDefaults.standard` под `timer_sync_state` (`TimerSyncService.swift:56, 452-462`) без account-scoping; SwiftData-таймеры прежнего аккаунта остаются (`TimerManager.swift:151-165`).
   - Impact: A выходит, B входит → отложенные события A (`timer_created`, `timer_started`) уходят на сервер под Bearer аккаунта B (`TimerSyncService.swift:224-285`) — в аккаунте B появляются таймеры-призраки, звонящие на всех устройствах B. Нарушение teardown-матрицы §3 ASYNC-LIFECYCLE.
   - Recommendation: `TimerSyncService.clearForLogout()` (сброс state + удаление `timer_sync_state`) и `TimerManager.clearForLogout()` (удаление SwiftData-строк + `timers = []`), вызывать из `stopForLogout()`.

4. **[Business Logic]** `replaceTimersFromServer` удаляет офлайн-созданные таймеры, если push не дошёл, а pull удался
   - `RecipeScalerNative/Services/TimerManager.swift:328-368`: merged строится только из серверного списка; локальные таймеры, отсутствующие на сервере, выпадают и удаляются из SwiftData. Защита есть только для pending-удалений (`TimerSyncService.swift:208-214`); `loadActiveTimersFromServer` продолжает pull даже при `flushPendingSyncImmediately()` с проглоченной ошибкой (`TimerSyncService.swift:200, 273, 282-284`).
   - Impact: таймер создан офлайн → POST вернул 5xx/`success=false` при рабочем GET → локальный таймер молча удалён из UI и SwiftData, хотя сервер о нём не знает. Тихая потеря пользовательских данных.
   - Recommendation: в `replaceTimersFromServer` сохранять локально-уникальные таймеры с несинхронизированными событиями в `state.pendingEvents`; либо прерывать pull, если после flush остались pending-создания.

5. **[Architecture]** God-объект `YjsSyncService` — 4693 строки, 107 функций, 18 зон ответственности
   - `RecipeScalerNative/Services/YjsSync/YjsSyncService.swift` — MARK-секции от Public API (`:349`) до Session test seams (`:4569`); рядом `DocumentManager.swift` — 1646 строк.
   - Impact: любая фича правит один файл — конфликтные merge'и, невозможность изолированного тестирования домена, риск регрессий критического пути синхронизации.
   - Recommendation: резать по существующим швам (`ShoppingListService`, `CollectionMutationsService`, `ExportImportCoordinator`, `RecipeImagePrefetcher`), инкрементально по одному домену за спеку.

6. **[Architecture]** Дублированная реализация deviceId мимо фасада `SharedDeviceId`
   - `RecipeScalerNative/Services/YjsSync/YjsSyncService.swift:321-327` — read-or-create deviceId с захардкоженным ключом `"deviceId"` и записью только в `UserDefaults.standard`, при этом `RecipeScalerCore/Auth/SharedDeviceId.swift` уже зеркалирует standard ↔ App Group. Тот же литерал — `RecipeScalerNative/ViewModels/AccountSettingsViewModel.swift:391`.
   - Impact: два источника правды — extension-процесс и апп могут создать разные id (сервер видит два «устройства»); `YjsSyncService.deviceId` фиксируется в init и не обновляется; `logoutDevice` молча пропускается при отсутствии ключа.
   - Recommendation: заменить на `SharedDeviceId.current()` в обоих местах (~10 строк).

7. **[Architecture]** `TimerManager` обходит инжектированные зависимости через `.shared`
   - `RecipeScalerNative/Services/TimerManager.swift:743,750` (`TimerSyncService.shared` в `syncEnqueue`), `:794,819,831,857` (`TimerLiveActivityCoordinator.shared`); при этом инжектируемое `liveActivity` (`:56`, присваивается в `:95`) не используется ни разу.
   - Impact: нарушение composition root-контракта; в тестах mock через init подменяет лишь часть путей, возможны два живых координатора.
   - Recommendation: использовать инжектированные `timerSync`/`liveActivity`; `.shared`-shims оставить только для AppIntents/previews.

8. **[Performance]** Перезагрузка widget timeline каждую секунду, пока тикает любой таймер
   - `RecipeScalerNative/Services/TimerManager.swift:457-476`: 1-секундный тик (`:53`, `:437-442`) на каждом тике ставит `snapshotNeedsRepublish = true` → `persistTimerSnapshot` (`:420-433`): JSON-энкод + запись в App Group (`RecipeScalerCore/Snapshots/TimerSnapshotStore.swift:28-33`) + `WidgetCenter.shared.reloadTimelines` (`:429`). Debounce 0.2с не коалесцирует 1с-тики.
   - Impact: на каждый тик будится widget extension; CPU/батарея всё время работы таймера.
   - Recommendation: релоадить только на смене контентного состояния (старт/пауза/завершение/overdue), посекундный отсчёт — нативный `Text(timerInterval:countsDown:)` в виджете; снапшот — при изменении набора таймеров или минутных границах.

### Medium

9. **[Security]** Bearer-токен прикрепляется к произвольному URL аватара без allowlist хоста
   - `RecipeScalerCore/Networking/APIClient.swift:115-136` (`recipeImageDownloadRequest`) ставит `Authorization: Bearer` на любой `remoteURL`; путь: `AvatarImageService.swift:31-38` ← `profileData.avatarUrl` с сервера (абсолютный URL принимается как есть: `AccountSettingsViewModel.swift:96-98`, `DiscoverAPI.swift:327-334`).
   - Impact: скомпрометированный/внешний `avatarUrl` уводит Bearer на сторонний хост и в его логи. Defense-in-depth, но API-контракт — готовый footgun.
   - Recommendation: валидировать host по allowlist (`Config.baseURL`/`universalLinkHosts`) перед добавлением auth-заголовков; внешним URL — ходить без заголовков (паттерн `PublicImageCacheService.swift:89`).

10. **[Security]** Legacy `x-user-id` продолжает использоваться как «кандидат в креды»
    - `RecipeScalerCore/Networking/APIClient.swift:166-171` и `:127-129`: при отсутствии Bearer подставляется сырой `userId`. Механизм считается legacy (cutoff spec 041 — `DebugSimulatorAutoLogin.swift:6`).
    - Impact: если хоть один endpoint принимает `x-user-id` как аутентификацию — spoofable auth-bypass по известному userId; как fallback маскирует ошибки конфигурации токена.
    - Recommendation: удалить fallback; неаутентифицированные вызовы остаются неаутентифицированными (401 → recovery через `unauthorizedHandler`).

11. **[Business Logic]** `syncPendingEvents` стирает по timerId все события, включая заенкюенные после отправки POST
    - `RecipeScalerNative/Services/TimerSyncService.swift:273-277`: `removeAll { syncedSet.contains(event.timerId) }` — события, заенкюенные пока POST был в полёте, удаляются не отправившись.
    - Impact: Pause улетел в POST → пользователь жмёт Resume → ack по timerId удаляет событие Resume → остальные устройства навсегда видят «пауза». Нарушение §2 ASYNC-LIFECYCLE.
    - Recommendation: удалять только отправленные события — сопоставление по снапшоту очереди перед POST (или `(timerId, timestamp)`).

12. **[Business Logic]** «Light revoke» при transient-ошибке стирает seed-фразу — восстановление сессии невозможно
    - `RecipeScalerNative/Services/AuthService.swift:451-456`: ветка `.transient` вызывает `wipeLocalSession(reason: .lightRevoke)`, а `wipeLocalSession` (`:490-491`) безусловно удаляет seed и `SharedAuthStore.clear()`, хотя docstring обещает «retry once the transient condition clears».
    - Impact: 401 от глюка балансировщика + сетевой сбой во время exchange → пользователь разлогинен, данные на месте, но недостижимы; silent-восстановление при старте невозможно. Противоречит cold-start-пути (`:343-355`, тест `testHealthCheck_transient_keepsSession`).
    - Recommendation: для `.transient` сохранять seed и userId для silent re-exchange; полный wipe — только для `userNotFound`/`staleSession`/explicit logout.

13. **[Business Logic]** FollowStore: оптимистичная мутация «чужого» профиля пишет в общий `status`, свежий refresh отбрасывается
    - `RecipeScalerNative/Services/FollowStore.swift`: `follow/unfollow/setPushOptIn` (53-90) перезаписывают единственное поле `status`; stale-guard проверяет только откат (111-113); `refresh` отбрасывает валидный ответ нового профиля: `guard !isFollowingPending else { return }` (`:39`).
    - Impact: Follow на профиле A (медленная сеть) → переход на B → ответ по B выброшен → на экране B показан follow-стейт A до повторного монтирования.
    - Recommendation: в `mutate` не применять optimistic-запись при `username != activeUsername`; в `refresh` кэшировать ответ и применять по завершении мутации.

14. **[Performance]** `prefetchPreviews` — полный O(N) проход и удаление кэша «безкартинных» рецептов на каждый collection refresh
    - `YjsSyncService.refreshCollectionEntries` (`YjsSyncService.swift:3978`) → `scheduleImagePrefetch` (`:3887-3914`) → `RecipeImageService.prefetchPreviews` (`RecipeImageService.swift:144-194`): свип удалений + `isVariantCached` (stat + 2 UserDefaults-чтения на вариант, ~4 syscall'а на рецепт) на каждое дебаунснутое обновление коллекции.
    - Impact: при активном синке — тысячи stat-вызовов и UserDefaults IPC за короткое окно; конкуренция с реальной загрузкой картинок на image-акторе.
    - Recommendation: гейтить по fingerprint набора `(id, imageUrl)` (как `cacheStatus(for:)` — memo `:63-71`); свип удалений по diff.

15. **[Performance]** `enforceSizeLimit` полностью пересканирует кэш-каталог после каждой скачанной картинки
    - `PublicImageCacheService.performFetch` → `enforceSizeLimit()` после каждого 200 (`PublicImageCacheService.swift:135`); реализация `:179-210` — `contentsOfDirectory` + resourceValues по каждому файлу + sort (лимит 150МБ, `:28`).
    - Impact: первая загрузка ленты из N картинок — O(N²) файловых операций на image-акторе.
    - Recommendation: троттлинг (раз в N минут / K загрузок) либо инкрементальный учёт размера.

16. **[Performance]** SpotlightIndexer: вечный 10-Гц поллинг с глубоким сравнением на MainActor
    - `RecipeScalerNative/Services/SpotlightIndexer.swift:50-70`: цикл каждые 100мс (`:67`) сравнивает `lastSeen != snapshot` по всем полям всех рецептов; обработчик `onChange` (`:56-58`) мёртв — `start()` выходит по `guard !isStarted` (`:45`).
    - Impact: постоянная фоновая нагрузка на main-акторе всё время жизни приложения.
    - Recommendation: `withObservationTracking` + `withCheckedContinuation` (перерегистрация на итерацию) либо подписка на сигнал «коллекция изменилась» из `YjsSyncService`.

17. **[Performance]** PublicCachedImageView валидирует hero-картинку по сети при каждом появлении
    - `PublicImageCacheService.ensureCached(url:allowNetwork:)` (`PublicImageCacheService.swift:40-49`): файл есть + `allowNetwork == true` → всегда полный GET с ревалидацией; `PublicCachedImageView.swift:103-109` вызывает с `allowNetwork: true` на каждом `.task(id:)`; consumer — `DiscoverRecipeView.swift:154-160`.
    - Impact: сетевой раунд-трип при каждом открытии/возврате на публичный рецепт; без ETag у CDN — полный ре-даунлоад.
    - Recommendation: TTL на ревалидацию per-URL; полная ревалидация — только по pull-to-refresh.

18. **[Architecture]** Сетевые вызовы прямо во View-слое, минуя ViewModels/store
    - `RecipeScalerNative/Views/AssistantSheet.swift:423,597,628,661,682,867` (`AssistantAPI.*`), `TelegramConnectionView.swift:199,221,236,255` (`TelegramAPI.*` + polling-таск), `ShoppingListView.swift:730,747` (`SharingAPI.*`), `RecipeDetailImageSection.swift:155,176` (`RecipeImageUploadAPI.*`), `YDocRecipeDetailView.swift:968` (`RecipeLLMParseAPI.*`); плюс `TelegramConnectionView.swift:197` — `AuthService.shared.userId` в production-методе.
    - Impact: оркестрация и поллинг в struct-View — нетестируемы без host-синхронизации; `AuthService.shared` ломает инъекцию.
    - Recommendation: вынести в ViewModel'ы (паттерн `AccountSettingsViewModel` уже есть), зависимости инжектить.

19. **[Architecture]** `UserDefaults.standard` вне OS-фасадов: сессия ассистента во View, nutrition-ключ мимо фасада
    - `RecipeScalerNative/Views/AssistantSheet.swift:440,443,497,975-979` — персист sessionThreadId прямо во View; `AccountSettingsViewModel.swift:125,244,249` — прямые записи nutrition-ключа при существующем фасаде `NutritionSettings` (`NutritionViewModeStorage.swift:39-43`), читают тот же ключ два View через `@AppStorage`.
    - Impact: 4+ точки доступа к одному ключу в разных слоях; инвариант «UserDefaults только в фасадах» размыт; при переезде на App Group (spec 066) легко пропустить место.
    - Recommendation: `AssistantSessionStore` (OS-фасад) + сеттер в `NutritionSettings`.

20. **[Architecture]** God-view `YDocRecipeDetailView` — 1846 строк
    - `RecipeScalerNative/Views/YDocRecipeDetailView.swift`: detail + edit mode + ingredients/nutrition + LLM-parse + image section; рядом `YDocIngredientsSection.swift` (1273 строки).
    - Impact: каждое изменение detail-экрана — правка и ревью 1800+ строк; read/edit-логика переплетена.

21. **[Standards]** Молчаливое глотание ошибки авто-стопа записи голоса
    - `RecipeScalerNative/Services/AssistantVoiceRecorder.swift:125-127` — `catch { markIdle() }` вокруг `try await stopCapture()`; в файле ноль вызовов `AppLog`.
    - Impact: сбой остановки/сборки аудио теряется — диктовка пропадает без диагностики; нарушение правил логирования ASYNC-LIFECYCLE.

22. **[Standards]** Захардкоженный русский placeholder в HomeWidget вне xcstrings, lint его не покрывает

### Low

## Что проверено и проблем не выявило

- **Security:** креды расширений через keychain access group, entitlements консистентны; plaintext-копии в UserDefaults вычищаются при старте; debug autologin недостижим в release; ATS-исключений нет; токены/seed не логируются; zip-импорт с тройными лимитами и без zip-slip; deep links — allowlist хостов + UUID-валидация; Socket.IO auth через событие, токен не в query.
- **Business Logic:** миграции GRDB v1-v6 корректны и идемпотентны; session-context guards в YjsSync аккуратны; epoch-гварды store'ов корректны; гонок в Shopping/RecipeEdit ViewModels не найдено; AuthServiceStaleSessionTests соответствует реализации (кроме находки №12).
- **Performance:** sync-слой (debounce 1с flush, 150мс collection refresh), поиск в списке (прекомпут вне body), GRDB-схема с индексами и WAL, DocumentManager вне main, UI-каунтдаун таймеров на `TimelineView` — ок.
- **Architecture:** расширения не тянут сервисы аппа и не копируют авторизацию; `.shared` во Views — почти весь `#Preview`; AppIntents `.shared` — разрешённая категория; watch уже на `RecipeScalerCore/TimerViews`.
- **Standards:** `lint-i18n.sh` PASS; `try!` только в `#Preview`; print/NSLog/пустых catch нет; `error.localizedDescription` в UI не утекает; AppIntents-ключи в xcstrings присутствуют.
