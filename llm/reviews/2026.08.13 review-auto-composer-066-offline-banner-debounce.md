# Code Review: 066-offline-banner-debounce

## Summary

Reviewed uncommitted work on `066-offline-banner-debounce` (debounced offline status banners via `OfflineBannerGate`, ~+67/−17 across app wiring + new unit tests + draft spec).

Areas reviewed: **Business Logic**, **Architecture / DI**, **Standards**.  
Skipped: **Security** (no user input / auth / secrets), **Performance** (single MainActor `Task.sleep`, no hot path / DB / allocations of concern).

**Overall risk: high.** Gate FSM, composition-root DI, and unit tests for the arm/hide/re-arm matrix look solid, but the primary user story (no flash on unlock) is still broken for typical lock durations because background disconnect arms the gate and `!isConnected` keeps it visible through `.connecting` until `.connected`.

## Findings (sorted by priority)

### Critical

1. **[Business Logic]** Background disconnect arms the gate; unlock after >3s still flashes banners
   - Flow: lock → `handleEnteredBackground()` → `.disconnected` (`app_background`) → `offlineGate.update(true)` → arm sleep completes while backgrounded (or drains immediately on resume) → `isVisible = true`. On unlock FSM is still `.disconnected`/`.connecting`; because the signal is `!isConnected`, `.connecting` does **not** disarm → banners stay until `.connected`. That is the US1 / SC-001 flash the feature exists to stop (debounce only helps when background <3s).
   - Impact: Common phone lock >3s → brief offline banners on unlock even when network is fine and reconnect finishes in <1s.
   - Recommendation: Do not treat lifecycle disconnect as durable offline for the gate — e.g. suppress while `scenePhase != .active`, or skip arm when reason is `app_background`, and on `.active` re-arm from current state with a fresh 3s window so reconnect can cancel before show. Add a test covering background-arm → resume → reconnect-within-threshold → never visible.

### High

2. **[Standards]** Spec still says `networkReachable` drives the gate (Key entities / Downstream consumers)
   - FR-007 / Assumptions / `AppShellView` correctly use `!connectionState.isConnected`; Key entities (~line 162) and Downstream consumers still describe NWPathMonitor as the gate signal.
   - Impact: Future agents/humans will reintroduce the device-proven-unreliable NWPathMonitor path.
   - Recommendation: Align those sections with FR-007; keep FR-001 wording that `networkReachable` is retained unused by the gate.

3. **[Architecture / Standards]** Stale doc-comment on `YjsSyncService.networkReachable`
   - Comment still claims it is “used by `OfflineBannerGate` instead of `connectionState`” while runtime wiring uses `connectionState`.
   - Impact: Documents a false dependency edge next to the public API; invites the same wrong rewiring as (2).
   - Recommendation: Rewrite to FR-001/FR-007: exposed projection for future consumers; gate does **not** use it.

4. **[Standards]** `isHardOffline` naming / docs contradict the actual signal
   - Callers pass `!isConnected` (includes `.connecting` / `.reconnecting`). Spec Assumptions already note old hard-offline was too narrow; method docs and Edge Cases still talk «жёсткий офлайн» / `connectionState.isHardOffline` (API gone). US3 AS1 still says hide on `.connecting`/`.reconnecting`; code only hides on `.connected`.
   - Impact: Maintainers will “fix” by disarming on `.connecting`, which breaks airplane-mode arming.
   - Recommendation: Rename param (`isNotConnected` / `shouldArm`), update FR-004/005/Edge Cases/US3 AS1/tests to match FR-007.

### Medium

5. **[Architecture]** `AccountView.#Preview` does not inject `OfflineBannerGate`
   - View now reads `@Environment(OfflineBannerGate.self)`; preview only injects `coordinator` (and was already missing other `@Environment` services).
   - Impact: Xcode canvas crashes on first `offlineGate` access; production path via `.appEnvironment(container)` is fine. Pre-existing preview debt worsened by one dependency.
   - Recommendation: Prefer routing the preview through `.appEnvironment(container)`, or at least `.environment(OfflineBannerGate())`.

6. **[Standards]** `AGENTS.md` SPECKIT block still points at `specs/065-share-feedback/plan.md`
   - `.specify/feature.json` already points at `specs/066-offline-banner-debounce`, which has only `spec.md` (no `plan.md`).
   - Impact: Agents boot into the wrong feature context.
   - Recommendation: Point SPECKIT at `specs/066-offline-banner-debounce/spec.md` (or add `plan.md` and point there).

7. **[Standards]** User Story 2 body cites wrong i18n key for Shopping Share Sheet
   - US2 text says `account.public-profile.offline`; Boundaries table and code use `account.offline.alert`.
   - Impact: Misleading acceptance/copy check for that surface.
   - Recommendation: Fix US2 text to `account.offline.alert`.

### Low

_(none)_

## Verified clean (no findings in these checks)

- **Gate FSM**: cancel + `Task.isCancelled` + `[weak self]` closes stale completion; dedupe / re-arm / short-dip behavior correct under `@MainActor`.
- **Composition root**: constructed in `AppContainer`, injected via `.appEnvironment(_:)`, no `.shared`; single writer in `AppShellView` (`onChange` + `onAppear`).
- **Feature gating left instant**: `isOnline` / `connectionState.isConnected` consumers untouched as intended.
- **Unit tests**: cover listed positive invariants for the gate itself (do not encode the US1 background-sticky case).
- **i18n / pbxproj**: no new UI strings; both new files registered in the Xcode project.
- **Logging FR-004/007**: Assumptions explicitly say diagnostic `offline_banner_*` / `connection_state_*` logs were removed after device confirmation — not a gap vs current spec.

## Recommendation

**Changes Requested.**

Blocker: fix critical #1 (background arm → unlock flash) so US1 holds for lock durations >3s; then align docs/naming (#2–#4) so the signal choice cannot be silently reverted. Preview (#5) and SPECKIT/US2 copy (#6–#7) can land in the same pass or follow-up.
