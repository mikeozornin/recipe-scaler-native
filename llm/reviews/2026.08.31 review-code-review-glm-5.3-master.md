# Code Review: c78e37f (master)

- **Коммит**: `c78e37f` — `fix(db): create Application Support before opening on-disk SQLite`
- **Ревьюеры**: два изолированных сабагента (логика/тесты; архитектура/стандарты), модель GLM-5.3
- **Области**: Business Logic, Test Quality, Architecture, Standards. Security и Performance не запускались — коммит не трогает пользовательский ввод, авторизацию и горячие пути (одно создание директории на старте).

## Summary

Продакшн-изменение корректное и минимальное: `createDirectory(at:withIntermediateDirectories:)` идемпотентен для существующей директории, все новые сценарии отказа (файл на пути, права) ранее тоже падали в `sqlite3_open_v2`, а выброс ошибки попадает в тот же `catch` в `AppContainer` → `logInitFailure` → in-memory fallback, т.е. контракт деградации сохранён. Тест-сим `directory: URL?` кохезивен рядом с существующими `makeInMemoryForTesting()` / `makeInMemoryFallback()`, pbxproj-обвязка корректна, docs не устарели. Находки — только усиление тестов и мелкая диагностика, блокирующих нет.

## Findings (sorted by priority)

### Medium

1. **[tests]** `YrsDatabaseInitTests.swift:65-73` — `testReopenOnSameDirectorySucceeds` заявляет проверку «idempotence across launches», но проверяет только «второй init не бросил + файл существует», что уже покрыто первым тестом. Инвариант, уникальный для перезапуска — данные, записанные до закрытия, читаются после повторного открытия — не проверяется.
   - Impact: регрессия, ломающая повторное открытие (мигратор бросает на уже мигрированной базе, смена journal mode) пройдёт этот тест молча; нарушает `docs/TESTING.md` §1 (проверка «отсутствия падения» вместо ожидаемого действия).
   - Recommendation: записать строку через первый инстанс, отпустить его, переоткрыть вторым `YrsDatabase(directory:)` и прочитать строку обратно (`SELECT COUNT(*) FROM recipe_sync_state` == 1).

2. **[process]** Отсутствует postmortem по багу. Регрессия «первый запуск → SQLITE_CANTOPEN → тихий in-memory fallback → потеря всех оффлайн-правок первой сессии» жила на master c июня 2026; по `docs/TESTING.md` §6 такой случай требует записи в `docs/DECISIONS.md` или `specs/`.
   - Impact: урок (почему месяцами никто не замечал, что флаг `dbInitFailed` не проверялся в первый запуск / не было инварианта «fresh install → on-disk») не зафиксирован; риск повтора класса ошибки.
   - Recommendation: добавить короткий postmortem: симптом, root cause, почему тесты не ловили, какое поведение теперь гарантировано.

### Low

3. **[tests]** Нет edge-теста на новую достижимую ошибку `createDirectory`: путь занят обычным файлом.
   - Impact: если позже кто-то «починит» выброс в тихий внутренний fallback внутри `init`, ничего не заметит; `docs/TESTING.md` §4 требует edge-тесты на новые failure-пути.
   - Recommendation: тест, создающий файл по пути `freshDir`, с `XCTAssertThrowsError(try YrsDatabase(directory: fileURL))` — ошибка обязана дойти до `AppContainer`, где единственная точка восстановления.

4. **[diagnostics]** `Database.swift` — `logInitFailure` помечает все ошибки init как «Failed to open on-disk database»; после коммита ошибки создания директории попадают в то же сообщение.
   - Impact: при триаже смешиваются стадии отказа (mkdir vs sqlite open).
   - Recommendation: логировать стадию (например, отдельное сообщение для createDirectory) или включать контекст ошибки.

5. **[standards]** `YrsDatabaseInitTests.swift` использует GRDB extension API (`db.execute`, `Int.fetchOne`) без `import GRDB`; компилируется через транзитивный импорт, но соседние три тест-файла его импортируют явно.
   - Impact: хрупкость при изменении видимости транзитивных импортов, несоответствие конвенции соседних файлов.
   - Recommendation: добавить `import GRDB`.

## Recommendation

**Approved** — продакшн-фикс корректный, контракт fallback сохранён, регрессионные тесты есть. Находки 1–3 стоит адресовать follow-up коммитом (усиление тестов + postmortem), 4–5 — по желанию.
