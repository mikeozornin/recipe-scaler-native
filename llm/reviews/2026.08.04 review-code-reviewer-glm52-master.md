#### 3. [architecture] Coordinator's `Standalone` is built with a fresh `LiveActivityPushRegistrar()`, breaking the project's own shim convention

**Status: ✅ Fixed via finding 4.** With `LiveActivityPushRegistrar.shared` /
`LiveActivityPushRegistrar.Standalone` deleted, the coordinator's `Standalone` legitimately
owns its private `LiveActivityPushRegistrar()` instance — there is no longer a divergent
second instance to worry about. Original finding retained below for context.

`TimerLiveActivityCoordinator.swift:21-23`:

```swift
private static let Standalone = TimerLiveActivityCoordinator(
    pushRegistrar: LiveActivityPushRegistrar()
)
```

The established convention (cf. `PushRegistrationService.swift:22`:
`PushRegistrationService(auth: AuthService.shared)`) is that a child service's `Standalone` is
built with **`.shared` shims of its dependencies**, not fresh instances. Here,
`TimerLiveActivityCoordinator.Standalone` constructs `LiveActivityPushRegistrar()` while
`LiveActivityPushRegistrar.shared` (pre-container) returns
`LiveActivityPushRegistrar.Standalone` — a **different instance**.

**Impact**: Today the two registrars are functionally equivalent because all state lives in
`UserDefaults.standard` (cross-instance visible). The moment the registrar gains any in-memory
state — and `pushTokenRetryAfter` / epoch tracking in the coordinator suggests that's the
natural next refactor — the two instances silently diverge. This is exactly the class of
regression the project's "no hidden cross-singleton wiring" rule in `AppContainer.swift:9` is
meant to prevent. There's also a latent trap if a future caller invokes
`LiveActivityPushRegistrar.shared` to inspect cache state: they'd see a different cache from
the one the coordinator's Standalone is mutating.

**Recommendation**: Either (a) construct the coordinator's `Standalone` with
`LiveActivityPushRegistrar.shared` to match the convention, or — preferred — see finding 4.

#### 4. [architecture] `LiveActivityPushRegistrar.shared` shim is unused — speculative surface area

**Status: ✅ Fixed.** Deleted `LiveActivityPushRegistrar.shared` and
`private static let Standalone` from the registrar. The class is now a plain
`@MainActor final class` conforming to `LiveActivityPushRegistering`, constructed only in
`AppContainer.init` and (for the coordinator's pre-bootstrap path) inside
`TimerLiveActivityCoordinator.Standalone`. Repo-wide grep confirms zero callers — safe to
remove. Original finding retained below for context.

A repo-wide search for `LiveActivityPushRegistrar.shared` returns **zero callers**. The
registrar is consumed exclusively via constructor injection into the coordinator. No AppIntent,
extension, or pre-bootstrap call site reads it.

`LiveActivityPushRegistrar.swift:13-21`:

```swift
static var shared: LiveActivityPushRegistrar {
    if let container = AppContainer.shared {
        return container.liveActivityPushRegistrar
    }
    return Standalone
}

private static let Standalone = LiveActivityPushRegistrar()
```

**Impact**: This adds a public singleton surface that nothing exercises, plus a second
`Standalone` instance that can drift from the one embedded in
`TimerLiveActivityCoordinator.Standalone` (see finding 3). It violates the project's own
composition-root principle: `AppContainer.swift:8-9` — *"Services are constructed in dependency
order with explicit `init(...)` parameters — no hidden cross-singleton wiring."* Adding the shim
"for symmetry with other services" is YAGNI; the spec (`spec.md:269-272`) describes the
registrar purely as an injected dependency, not a process-wide singleton.

**Recommendation**: Delete `LiveActivityPushRegistrar.shared` and
`private static let Standalone`. The class becomes a plain `@MainActor final class` constructed
only in `AppContainer` and (for the coordinator's pre-bootstrap path) inside
`TimerLiveActivityCoordinator.Standalone`. If a real AppIntent / extension caller arrives
later, add the shim then. This also collapses finding 3: with no `.shared` on the registrar,
the coordinator's `Standalone` legitimately owns its private registrar instance.

### Medium

#### 5. [architecture] `TimerLiveActivityCoordinator` is approaching "God class" — push-token lifecycle is a separable concern

The class is now 535 lines managing nine distinct state concerns:

| Concern | State | Lines |
|---------|-------|-------|
| Activities cache | `activityByTimerId` | 39, 76-114, 137-186 |
| Failure backoff (ActivityKit) | `failureTimestamps` | 40, 129-132, 184, 202, 217, 432-437 |
| Priority eviction | `lowestPriorityEvictableActivity`, `priorityRank` | 343-416 |
| `activityUpdates` observation | `activityUpdatesTask` | 41, 446-475 |
| **Push-token observation** | `pushTokenTasks`, `pushTokenEpoch` | 43-45, 261-307 |
| **Push retry/backoff** | `pushTokenRetryAfter` | 47, 266-268, 291-300 |
| **Legacy push migration** | `createdWithPushTypeToken`, `pushTokenEmissionReceived`, `legacyMigrationTasks` | 49-53, 304-337 |
| Content-state construction | `makeAttributes`, `makeContentState`, `staleDate` | 479-534 |
| Cross-cutting `currentTimersById` reach-through into `AppContainer.shared.timer.timers` | — | 421-430 |

The bolded rows (push-token observation + retry + legacy migration) form a self-contained
sub-responsibility: they have their own invariants (epoch invalidation, idempotency via
`hasCachedToken`, 8s migration timeout, 30s retry backoff), their own task lifecycle, and they
interact with the rest of the class only through a small surface
(`startObservingPushToken`, `stopObservingPushToken`, `hasCachedToken`, plus the `end` paths
that call `stopObservingPushToken`).

**Impact**: The class has outgrown the "one cohesive responsibility" framing in spec 044/058.
New push-related state added in 058 is interleaved with ActivityKit-budget logic in
`sync(timer:)` and `end(timerId:)`, making both harder to reason about. The epoch-invalidation
dance (`TimerLiveActivityCoordinator.swift:278-289`) is particularly subtle and would benefit
from being testable in isolation.

**Recommendation**: Extract a `LiveActivityPushTokenObserver` collaborator:

```swift
@MainActor
final class LiveActivityPushTokenObserver {
    init(registrar: LiveActivityPushRegistrar,
         resolveActivity: (String) -> Activity<RecipeTimerActivityAttributes>?,
         onLegacyMigrationTimeout: (String) async -> Void)

    func observe(activity:for:scheduleLegacyMigration:)
    func stop(timerId:)
    func stopAll()
}
```

The coordinator then holds `pushTokenObserver: LiveActivityPushTokenObserver` and delegates the
four `start/stop` call sites. This shrinks the coordinator back to ~350 lines, isolates the
legacy-migration backoff state, and makes the epoch invalidation unit-testable without standing
up the full ActivityKit stack.

#### 6. [architecture + security] Token cache clearing on logout is indirect and leaks on partial failure

**Status: ✅ Fixed.** Added `LiveActivityPushRegistrar.clearAllCachedTokens()` and wired it
directly into `AppContainer.stopForLogout()` alongside `featureAdoption.clearForLogout()`. This
makes the registrar self-contained for its own persistence lifecycle and resilient to partial
`endAll()` failures. Also covered by `testClearAllCachedTokens_WipesAllPrefixedEntries`.
Original finding retained below for context.

The registrar owns persisted state with prefix `"liveActivityPushToken.<timerId>"` in
`UserDefaults.standard` (`LiveActivityPushRegistrar.swift:24, 31, 41, 61, 80`). Clearing this
state depends on a three-hop call chain:

`AppContainer.stopForLogout()` (`AppContainer.swift:388-398`) →
`timerLiveActivityCoordinator.endAll()` (`TimerLiveActivityCoordinator.swift:237-248`) →
`end(timerId:)` (`:216-231`) → `pushRegistrar.unregister(timerId:)` (`:77-102`, which
`removeObject`s the key at line 80).

If `endAll()` is interrupted (process kill, MainActor never rescheduled before termination, an
activity's `activity.end` throws and aborts the loop), the `UserDefaults.standard` keys leak
across the account switch. The next user will see `hasCachedToken(timerId:)` return `true` for
the previous user's timerIds, which suppresses the legacy-push-migration path
(`TimerLiveActivityCoordinator.swift:321`) and can leave pre-058 activities stuck.

**Impact**: Spec 058 says tokens are scoped per `(userId, deviceId, timerId)` (R3); on the
client, the cache is keyed only by `timerId`, so cross-account leakage is real if `timerId`s
ever collide (UUIDs make this low-probability, but it's still architecturally wrong). Other
services that own persisted account-scoped state have a direct logout hook — e.g.
`FeatureAdoptionStore.clearForLogout()` (`FeatureAdoptionStore.swift:114`), called directly from
`stopForLogout()` (`AppContainer.swift:397`). The risk is amplified by any race where
`register` succeeds but `activityByTimerId` never gets populated (e.g. process killed between
`Activity.request` success at `TimerLiveActivityCoordinator.swift:200` and the cache
assignment).

**Recommendation**: Add an explicit `clearAllCachedTokens()` method on
`LiveActivityPushRegistrar` and call it directly from `AppContainer.stopForLogout()` alongside
`featureAdoption.clearForLogout()`:

```swift
// AppContainer.stopForLogout()
await timerLiveActivityCoordinator.endAll()
liveActivityPushRegistrar.clearAllCachedTokens()   // belt-and-suspenders
featureAdoption.clearForLogout()
```

This makes the registrar self-contained for its own persistence lifecycle and resilient to
partial `endAll()` failures. Optionally also re-scope the UserDefaults key to include userId
(e.g. `"liveActivityPushToken.\(userId).\(timerId)"`) to fully match the server's per-user
uniqueness constraint from R3.

#### 7. [business-logic, confidence ~55] Late-success `unregister` may wipe a newer activity's row

`TimerLiveActivityCoordinator.swift:283-289`:

```swift
if Task.isCancelled || epochNow != epochAtStart {
    if ok {
        await self.pushRegistrar.unregister(timerId: timerId)
    }
    return
}
```

The "undo late success" mechanism keys `unregister` on `timerId`, not on the activity instance.
If a same-`timerId` activity B is created and its `pushTokenUpdates` emission is registered
*between* A's late `register` return and A's late `unregister` call, A's `unregister` will
DELETE B's row.

Confidence is only ~55 because:
- The window is the duration of A's `register` POST plus end's `unregister` POST — typically
  200 ms–2 s.
- For B to register in this window, B must be created, `pushTokenUpdates` must emit (Apple:
  "can take seconds"), and B's POST must succeed. Unlikely in the typical case.
- The triggering scenario (end → recreate same `timerId` within ms) is rare: `timerId` is a
  per-timer UUID; "restart" semantics for an exceeded timer is the only realistic path.

**Recommendation if you want to harden**: capture the `Activity` instance in the task and after
late success only `unregister` if
`self.activityByTimerId[timerId] !== activity && self.pushTokenTasks[timerId] == nil`. Or
simpler: drop the `unregister` and accept the rare zombie row — server TTL cleanup (R5) handles
it.

#### 8. [business-logic, confidence ~50] Failed-`register` recovery assumes `pushTokenUpdates` replays current token on re-subscribe

`TimerLiveActivityCoordinator.swift:291-298, 261-307`. After `register` returns `false`:
`pushTokenRetryAfter[timerId] = +30s`, `stopObservingPushToken(timerId:)` cancels the task and
clears `pushTokenTasks[timerId]`. Recovery depends on a later `sync(timer:)` calling
`startObservingPushToken` again, which creates a *new* Task that re-subscribes to
`activity.pushTokenUpdates`.

Apple does not document whether `pushTokenUpdates` replays the current token on re-subscribe.
If it does (the common assumption, parity with `activityUpdates`), recovery works. If it does
not, the activity will not be re-registered until the system rotates the token, which can be
hours or never — violating invariant R4 ("Activity.request success → POST register invoked").

**Recommendation**: confirm empirically on a real device (turn off server 058 endpoint, observe
whether second `POST` happens after 30s backoff). If it doesn't replay, persist the last-emitted
token hex in `UserDefaults` and POST it directly from a recovery path independent of the stream.
**Worth verifying before declaring spec 058 done.**

#### 9. [business-logic, confidence ~50] Fresh activity with `scheduleLegacyMigration: false` has no recovery if stream never emits

`TimerLiveActivityCoordinator.swift:204-208`. For freshly-created activities (with
`pushType: .token`), `scheduleLegacyMigration` is `false`. If `pushTokenUpdates` never emits
(e.g. APNs unreachable at request time and the device goes background before retry), no
migration timeout fires. The activity is alive but unregistered, violating invariant
"Activity.request success → POST register invoked" for that session.

Legacy/restored activities get the 8s migration timeout; fresh ones don't. Asymmetric.

**Recommendation**: schedule a softer "diagnostic" timeout (e.g. 30s) for fresh activities that
logs a `.notice` if no emission arrived, so QA can spot the failure mode during SC-001…003. No
need to end the activity — just observability.
