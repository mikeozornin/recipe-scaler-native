# Code Review: named_with_emoji feature-adoption flag

**Branch**: feature work on top of master (recipe-scaler-native + recipe-scaler-web)
**Model**: GLM-5.2 (composer-2.5)
**Date**: 2026-08-08

## Summary

Three parallel review subagents covered Business Logic + Standards, Security, and Architecture + Performance. No critical or high-severity findings. The change is **approved for release** with optional low-priority cleanups.

**Areas reviewed**: emoji detection semantics, save-path trigger correctness, backfill logic, Swift cache backward-compat, API/authorization posture, ReDoS / exception safety, module boundaries, contract TS↔Swift symmetry, performance of trigger and backfill.

**Areas skipped**: none — change is small and focused, all three relevant lenses applied.

**Overall risk**: low. The new flag is a cosmetic progress indicator; the trigger piggybacks on the existing idempotent `featureAdoptionService.mark()` path, detection delegates to the already battle-tested `getLeadingEmoji`, and Swift cache migration is fully backward-compatible.

## Findings (sorted by priority)

### Medium

1. **[architecture/performance]** Per-save `mark('named_with_emoji')` diverges from the one-shot observer pattern used by the other three Yjs-derived flags (`created_collection`, `shared_recipe`, `used_shopping_list`).
   - Impact: Those flags attach a Yjs observer that fires once, unobserves, and never hits the DB again. `named_with_emoji` instead runs `INSERT ... ON CONFLICT DO NOTHING` on every save where the name has emoji. Idempotent, but a wasted DB roundtrip per debounced save for the lifetime of the user's session. At prod scale (debounced saves × active users × recipe/folder mutations) this is real load on the adoption table for zero new information after the first hit.
   - Recommendation: Either (a) accept the cost since `mark()` is cheap and saves are debounced — document the deliberate divergence, or (b) convert to the one-shot observer pattern: observe `recipe.name` and `folders` array, mark on first emoji-name detection, unobserve. Option (a) is acceptable for v1 ship; revisit if adoption-write volume shows up in metrics.

2. **[architecture]** Backfill `--only-emoji` control flow has become spaghetti inside the shared `phase2Yjs` body.
   - Impact: Readability and future maintenance risk. The single function now serves two modes with `if (!onlyEmoji && …)` sprinkled across collection/recipe/shopping branches plus a mid-function `continue` shortcut for `--only-emoji`. Next person adding a flag will struggle to reason about both modes at once.
   - File: `server/scripts/backfill-feature-adoption.ts:539–725`.
   - Recommendation: Extract `phase2EmojiOnly(supabase)` as a separate function that only loops users and checks emoji names. Keep `phase2Yjs` for the full Phase-2 pass. Each function becomes linear and readable.

### Low

3. **[business logic]** Dry-run script scans collection `recipes` entries for emoji names, but the production backfill scans only `folders`.
   - File: `server/scripts/dry-run-named-with-emoji.mjs:113–120` vs `server/scripts/backfill-feature-adoption.ts:584`.
   - Impact: Dry-run "WOULD flag" count can exceed what `--apply --only-emoji` actually writes, making the dry-run a misleading predictor. In our local run this likely inflated the 12-count (all 12 came back as `viaCollection`).
   - Recommendation: Since the dry-run is a throwaway, either delete it before commit (user's stated intent) or align its collection-doc scan to `folders` only.

4. **[architecture/performance]** `folders.toArray()` allocates a full JS array on every collection save.
   - File: `server/src/services/yjs-service.ts:1147–1160` (live trigger).
   - Impact: For users with many folders, a small extra allocation on the hot save path. Negligible per save, debounced anyway.
   - Recommendation: Optional — iterate `folders` in place via index loop instead of `toArray()`. Low value, only if you're already touching this code.

5. **[architecture/performance]** Backfill iterates all users × all their recipe docs.
   - File: `server/scripts/backfill-feature-adoption.ts:560–648`.
   - Impact: At prod scale (thousands of users, ~1500 recipes) the per-user scan walks every recipe doc. Local run was 1s/220 users; linear extrapolation puts prod in the low-minute range, acceptable for a one-shot idempotent script.
   - Recommendation: Optional early-exit — once `hasEmojiName` becomes true from either the collection `folders` scan or the first matching recipe, `break` the recipe loop. Current code already does this in `--only-emoji` mode; extending the same early-exit to the full Phase 2 mode would shave time.

6. **[business logic]** `namedWithEmoji` enum position (mid-list, after `createdCollection`) contradicts the spec table and contract doc which append it last.
   - File: `RecipeScalerNative/Models/FeatureAdoptionItem.swift:12–20` vs `specs/038-feature-adoption-tracker/spec.md` feature table and `contracts/feature-adoption-api.md` FEATURE_KEYS list.
   - Impact: The enum doc-comment claims "`allCases` order matches the spec table order", which is no longer literally true. This was an intentional UX decision (per user request: "пункт надо поднять под создать коллекцию"), so functionally correct — only the docs disagree.
   - Recommendation: Reconcile the spec/contract docs to explicitly note "rendering order intentionally differs from FEATURE_KEYS canonical order". One-line doc edit, no code change.

7. **[business logic]** No regression test for the hand-written `init(from:)` Codable backward-compat path.
   - File: `RecipeScalerNative/Services/FeatureAdoptionStore.swift:68–81`.
   - Impact: The 10-key → 11-key cache migration is currently verified by inspection only. A future refactor that switches `decodeIfPresent` to `decode` would silently break old caches.
   - Recommendation: Add a small test decoding `{"installedNativeApp":true}` (10 keys, no `namedWithEmoji`) and asserting `report.namedWithEmoji == false` while legacy `true` values survive.

8. **[standards]** Indentation regression on the new `only-emoji` log line.
   - File: `server/scripts/backfill-feature-adoption.ts:156`.
   - Impact: Cosmetic — the line has a 2-space leading indent that breaks column alignment of the surrounding `console.log` block.
   - Recommendation: Remove the leading 2 spaces.

9. **[architecture]** Comment drift: `feature-adoption-service.ts` header now says "two Yjs listeners" but the list grew to three with `named_with_emoji`.
   - File: `server/src/services/feature-adoption-service.ts:4–14`.
   - Impact: Documentation accuracy only.
   - Recommendation: Update the comment to "three Yjs listeners" or drop the count entirely.

10. **[standards/hygiene]** Throwaway dry-run script duplicates the leading-emoji regex inline instead of importing the helper.
    - File: `server/scripts/dry-run-named-with-emoji.mjs:18–24`.
    - Impact: If the script is ever committed, the duplicated regex will drift from `shared/utils/recipe-title-emoji.ts`.
    - Recommendation: Do not commit (user's stated intent). If it stays, import `hasLeadingEmoji` from the helper instead of re-declaring the regex.

## Recommendation

**Approved for release.**

No blocking findings. All issues are low- or medium-priority cleanup. Recommended pre-merge actions (all optional, can ship without):

- Delete `server/scripts/dry-run-named-with-emoji.mjs` (throwaway, not intended for repo).
- Fix the 2-space indent regression in `backfill-feature-adoption.ts:156` (1 line).

Recommended post-merge follow-ups:

- Add Swift test for legacy cache decode path (finding 7).
- Reconcile spec table vs enum ordering doc (finding 6).
- Consider converting the per-save `mark()` to one-shot observer if adoption-write volume becomes noticeable (finding 1).
- Consider extracting `phase2EmojiOnly` next time the backfill script is touched (finding 2).
